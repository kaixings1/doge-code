# 多代理架构模式

多代理架构将工作分布到多个语言模型实例，每个实例拥有自己的上下文窗口。设计得当时，这种分布能够实现超越单代理限制的能力。设计不当时，会引入抵消收益的协调开销。关键洞察是：子代理主要存在于隔离上下文，而非拟人化的角色分工。

## 使用时机
在此情况下激活此技能：
- 单代理上下文限制制约了任务复杂度
- 任务自然分解为并行子任务
- 不同子任务需要不同的工具集或系统提示
- 构建必须同时处理多个领域的系统
- 将代理能力扩展到单上下文限制之外
- 设计包含多个专业化组件的生产代理系统

## 核心概念
多代理系统通过分布解决单代理上下文限制。三种主流模式：监督者/编排器（集中控制）、对等/swarm（灵活交接）、以及分层（分层抽象）。关键设计原则是上下文隔离——子代理主要存在于分隔上下文而非模拟组织角色。

有效的多代理系统需要明确的协调协议、避免谄媚的共识机制，以及对故障模式（瓶颈、发散、错误传播）的仔细关注。

## 详细主题
### 为什么需要多代理架构
**上下文瓶颈**：单代理面临推理能力、上下文管理和工具协调的固有上限。任务越复杂，上下文窗口填满累积历史、检索文档和工具输出。性能按可预测模式下降：中间丢失效应、注意力稀缺和上下文污染。

多代理架构通过将工作分区到多个上下文窗口解决这些限制。每个代理在专注于其子任务的干净上下文中运行。结果在协调层聚合，没有任何单上下文承担全部负担。

**令牌 经济学现实**：多代理系统消耗的 令牌 显著多于单代理方法。

### 模式一：监督者/编排器
集中式编排器将输入分解为子任务，分发给专门代理，综合结果。适用于需要强一致性和审计追踪的工作流。

### 模式二：对等/Swarm
代理自主交接任务。适用于开放式、动态工作负载。需要处理收敛和循环问题。

### 模式三：分层架构
抽象层级使高层策略与低层执行分离。适用于复杂、多层次的问题空间。
