# 设计接口（Design an Interface）

基于《软件设计的哲学》中的 "Design It Twice"：你的第一个想法不太可能是最好的。生成多种截然不同的设计，然后比较。

## 流程

### 1. 收集需求

设计之前，理解：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 关键操作是什么？
- [ ] 有什么约束？（性能、兼容性、现有模式）
- [ ] 什么应该隐藏在内部 vs 暴露？

问："这个模块需要做什么？谁将使用它？"

### 2. 生成设计（并行子代理）

使用 Task 工具同时生成 3+ 个子代理。每个必须产生一个**截然不同的**方法。

```
每个子代理的提示模板：

为一个模块设计接口：[模块描述]

需求：[收集的需求]

此设计的约束：[为每个代理分配不同的约束]
- 代理 1："最小化方法数量 — 目标 1-3 个方法"
- 代理 2："最大化灵活性 — 支持许多用例"
- 代理 3："优化最常见情况"
- 代理 4："从 [特定范式/库] 获取灵感"

输出格式：
1. 接口签名（类型/方法）
2. 用法示例（调用者如何使用）
3. 此设计内部隐藏什么
4. 这种方法论的权衡
```

### 3. 呈现设计

展示每个设计：

1. **接口签名** — 类型、方法、参数
2. **用法示例** — 调用者实际如何使用它
3. **它隐藏什么** — 保持内部的复杂性

按顺序呈现设计，以便用户在比较之前吸收每种方法。

### 4. 比较设计

展示所有设计后，比较它们：

- **接口简单性**：更少的方法、更简单的参数
- **通用 vs 专用**：灵活性 vs 焦点
- **实现效率**：形状是否允许高效的内部实现？
- **深度**：小接口隐藏重要的复杂性（好）vs 大接口带薄实现（坏）
- **正确使用的容易性** vs **误用的容易性**

用散文讨论权衡，不用表格。突出设计最大的分歧点。

### 5. 综合

最好的设计通常结合多个选项的见解。问：

- "哪个设计最符合你的主要用例？"
- "其他设计的哪些元素值得纳入？"

## 评估标准

来自《软件设计哲学》：

**接口简单性**：方法更少、参数更简单 = 更容易学习和正确使用。

**通用性**：可以处理未来的用例而无需更改。但要小心过度一般化。

**实现效率**：接口形状是否允许高效的实现？或强迫笨拙的内部？

**深度**：小接口隐藏重要的复杂性 = 深层模块（好）。大接口带薄实现 = 浅层模块（避免）。

## 反模式

- 不要让子代理产生相似的设计 — 执行截然不同
- 不要跳过比较 — 价值在于对比
- 不要实施 — 这纯粹关于接口形状
- 不要根据实施工作量评估
