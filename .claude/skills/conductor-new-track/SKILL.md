# 新轨道

创建包含详细规格和分阶段实施计划的新轨道（功能、错误修复、杂务或重构）。

## 使用此技能的场景

- 处理新轨道任务或工作流时
- 需要新轨道的指导、最佳实践或检查清单时

## 不要使用此技能的场景

- 任务与新轨道无关时
- 需要此范围之外的领域或工具时

## 说明

- 明确目标、约束和所需输入。
- 应用相关最佳实践并验证结果。
- 提供可操作的步骤和验证方法。
- 如需详细示例，请打开 `resources/implementation-playbook.md`。

## 预检检查

1. 验证 Conductor 是否已初始化：
   - 检查 `conductor/product.md` 是否存在
   - 检查 `conductor/tech-stack.md` 是否存在
   - 检查 `conductor/工作流.md` 是否存在
   - 如果缺失：显示错误并建议先运行 `/conductor:设置`

2. 加载上下文文件：
   - 读取 `conductor/product.md` 获取产品上下文
   - 读取 `conductor/tech-stack.md` 获取技术上下文
   - 读取 `conductor/工作流.md` 获取 TDD/提交偏好

## 轨道分类

根据描述确定轨道类型或询问用户：

```
这是什么类型的轨道？

1. 功能 - 新功能
2. Bug - 修复现有问题
3. 杂务 - 维护、依赖、配置
4. 重构 - 不改变行为的代码改进
```

## 交互式规格收集

**关键规则：**

- 每次只问一个问题
- 在继续前等待用户响应
- 根据轨道类型定制问题
- 总共最多 6 个问题

### 功能轨道

**问题 1：功能摘要**

```
用 1-2 句话描述这个功能。
[如果提供了参数，确认："你想要：{参数}。是否正确？"]
```

**问题 2：用户故事**

```
谁会受益以及如何受益？

格式：作为 [用户类型]，我想要 [操作] 以便 [收益]。
```

**问题 3：验收标准**

```
这个功能完成时必须满足什么条件？

列出 3-5 条验收标准（每行一条）：
```

**问题 4：依赖**

```
这依赖任何现有代码、API 或其他轨道吗？

1. 无依赖
2. 依赖现有代码（请指明）
3. 依赖未完成的轨道（请指明）
```

**问题 5：范围边界**

```
哪些明确不在本轨道范围内？
（有助于防止范围蔓延）
```

**问题 6：技术考虑（可选）**

```
有任何特定的技术方法或约束吗？
（按回车跳过）
```

### Bug 轨道

**问题 1：Bug 摘要**

```
什么出了问题？
[如果提供了参数，确认]
```

**问题 2：复现步骤**

```
如何复现这个 bug？
列出步骤：
```

**问题 3：预期与实际行为**

```
应该发生什么 vs 实际发生了什么？
```

**问题 4：影响范围**

```
系统的哪些部分受影响？
```

**问题 5：根因假设（可选）**

```
对原因有任何假设吗？
（按回车跳过）
```

### 杂务/重构轨道

**问题 1：任务摘要**

```
需要做什么？
[如果提供了参数，确认]
```

**问题 2：动机**

```
为什么需要这项工作？
```

**问题 3：成功标准**

```
我们如何知道这项工作完成了？
```

**问题 4：风险评估**

```
可能出什么问题？有任何风险性变更吗？
```

## 轨道 ID 生成

生成格式为 `{短名称}_{YYYYMMDD}` 的轨道 ID

- 从功能/bug 摘要中提取短名称（2-3 个词，小写，连字符）
- 使用当前日期
- 示例：`user-auth_20250115`、`nav-bug_20250115`

验证唯一性：

- 检查 `conductor/tracks.md` 中是否存在相同 ID
- 如果冲突，追加计数器：`user-auth_20250115_2`

## 规格生成

创建 `conductor/tracks/{trackId}/spec.md`：

```markdown
# 规格：{轨道标题}

**轨道 ID：** {trackId}
**类型：** {功能|Bug|杂务|重构}
**创建日期：** {YYYY-MM-DD}
**状态：** 草稿

## 总结

{1-2 句摘要}

## 上下文

{来自 product.md 的与此轨道相关的产品上下文}

## 用户故事（针对功能）

作为 {用户}，我想要 {操作} 以便 {收益}。

## 问题描述（针对 Bug）

{Bug 描述、复现步骤}

## 验收标准

- [ ] {标准 1}
- [ ] {标准 2}
- [ ] {标准 3}

## 依赖

{列出依赖或"无"}

## 范围外

{明确排除的内容}

## 技术说明

{技术考虑或"未指定"}

---

_由 Conductor 生成。根据需要审查和编辑。_
```

## 计划生成

规格批准后，生成 `conductor/tracks/{trackId}/plan.md`：

### 计划结构

```markdown
# 实施计划：{轨道标题}

**轨道 ID：** {trackId}
**规格：** spec.md
**创建日期：** {YYYY-MM-DD}
**状态：** [ ] 未开始

## 概述

{实施方法的简要总结}

## 阶段 1：{阶段名称}

{阶段描述}

### 任务

- [ ] 任务 1.1：{描述}
- [ ] 任务 1.2：{描述}
- [ ] 任务 1.3：{描述}

### 验证

- [ ] {阶段 1 的验证步骤}

## 阶段 2：{阶段名称}

{阶段描述}

### 任务

- [ ] 任务 2.1：{描述}
- [ ] 任务 2.2：{描述}

### 验证

- [ ] {阶段 2 的验证步骤}

## 阶段 3：{阶段名称}（如果需要）

...

## 最终验证

- [ ] 所有验收标准已满足
- [ ] 测试通过
- [ ] 文档已更新（如果适用）
- [ ] 准备好审查

---

_由 Conductor 生成。任务将标记为 [~] 进行中和 [x] 已完成。_
```

### 阶段指南

- 将相关任务分组到逻辑阶段
- 每个阶段应可独立验证
- 每个阶段后包含验证任务
- TDD 轨道：在实现任务前包含测试编写任务
- 典型结构：
  1. **设置/基础** - 初始脚手架、接口
  2. **核心实现** - 主要功能
  3. **集成** - 与现有系统连接
  4. **完善** - 错误处理、边界情况、文档

显示生成的计划并询问：

## 轨道创建

计划批准后：

1. 创建目录结构：

   ```
   conductor/tracks/{trackId}/
   ├── spec.md
   ├── plan.md
   ├── metadata.json
   └── index.md
   ```

2. 创建 `metadata.json`：

   ```json
   {
     "id": "{trackId}",
     "title": "{轨道标题}",
     "type": "feature|bug|chore|refactor",
     "status": "pending",
     "created": "ISO_TIMESTAMP",
     "updated": "ISO_TIMESTAMP",
     "phases": {
       "total": N,
       "completed": 0
     },
     "tasks": {
       "total": M,
       "completed": 0
     }
   }
   ```

3. 创建 `index.md`：

   ```markdown
   # 轨道：{轨道标题}

   **ID：** {trackId}
   **状态：** 待处理

   ## 文档

   - 规格
   - 实施计划

   ## 进度

   - 阶段：0/{N} 已完成
   - 任务：0/{M} 已完成

   ## 快捷链接

   - 返回轨道列表
   - 产品上下文
   ```

4. 在 `conductor/tracks.md` 中注册：
   - 向轨道表添加行
   - 格式：`| [ ] | {trackId} | {title} | {created} | {created} |`

5. 更新 `conductor/index.md`：
   - 将轨道添加到"活跃轨道"部分

## 完成消息

```
轨道创建成功！

轨道 ID：{trackId}
位置：conductor/tracks/{trackId}/

已创建文件：
- spec.md - 需求规格
- plan.md - 分阶段实施计划
- metadata.json - 轨道元数据
- index.md - 轨道导航

下一步：
1. 检查 spec.md 和 plan.md，进行任何编辑
2. 运行 /conductor:implement {trackId} 开始实施
3. 运行 /conductor:status 查看项目进度
```

## 错误处理

- 如果目录创建失败：停止并报告，不在 tracks.md 中注册
- 如果任何文件写入失败：清理部分轨道，报告错误
- 如果 tracks.md 更新失败：警告用户手动注册轨道
