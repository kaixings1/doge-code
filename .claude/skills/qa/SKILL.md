# QA 会话（QA 会话）

运行一个交互式 QA 会话。用户描述他们遇到的问题。你进行澄清、探索代码库获取上下文，并将问题提交为耐用、以用户为中心、使用项目领域语言的 GitHub issue。

## 对于用户提出的每个问题

### 1. 倾听并轻度澄清

让用户用自己的话描述问题。最多问 **2-3 个简短的澄清问题**，重点聚焦在：

- 他们期望什么 vs 实际发生了什么
- 复现步骤（如果不明显的话）
- 是稳定的还是间歇性的

**不要过度追问。** 如果描述足够清晰可以提交，就继续下一步。

### 2. 在后台探索代码库

与用户交谈的同时，在后台启动一个子代理（subagent_type=Explore）来理解相关领域。目的不是找修复方案 — 而是为了：

- 学习该领域使用的领域语言（检查 UBIQUITOUS_LANGUAGE.md）
- 理解功能应该做什么
- 识别用户可见的行为边界

这些上下文帮助你写出更好的 issue — 但 issue **本身不应该引用** 特定文件、行号或内部实现细节。

### 3. 评估范围：单个问题还是拆分？

提交之前，决定这是一个**单个 issue** 还是需要**拆分成多个 issue**。

在以下情况下拆分：

- 修复跨越多个独立领域（例如"表单验证错误 AND 成功消息缺失 AND 重定向损坏"）
- 存在明显可分离的关注点，不同的人可以并行处理
- 用户描述的内容有多个明显的失败模式或症状

在以下情况下保持为一个 issue：

- 是一处错误的行为
- 症状都是由同一个根本原因引起的

### 4. 提交 GitHub issue

使用 `gh issue create` 创建 issue。**不要**先让用户审阅 — 直接提交并分享 URL。

Issue 必须是**耐用的**— 即使经过重大重构后仍然有意义。从用户视角撰写。

#### 单个 issue

使用此模板：

```
## 发生了什么

[用通俗语言描述用户实际遇到的行为]

## 我的期望

[描述期望的行为]

## 复现步骤

1. [具体的、编号的、开发者可以跟随的步骤]
2. [使用项目领域术语，不要用内部模块名称]
3. [包含相关的输入、标志或配置]

## 额外上下文

[用户的任何额外观察或代码库探索中有助于框架化问题的信息 — 例如 "这仅在 Docker 层发生时出现，而在文件系统层不会" — 使用领域语言但不要引用文件]
```

#### 拆分（多个 issue）

按依赖顺序创建 issue（阻塞项优先），这样你可以引用真实的 issue 编号。

每个子 issue 使用此模板：

```
## 父级 issue

#<父级issue编号>（如果你创建了一个跟踪 issue）或 "在 QA 会话期间报告"

## 问题

[描述这个具体的行为问题 — 仅此部分，不要包含整个报告]

## 我的期望

[对此特定部分的期望行为]

## 复现步骤

1. [针对此 issue 的特定步骤]

## 被阻塞于

- #<issue编号>（如果此 issue 需要另一个问题解决后才能修复）

或 "无 — 可以立即开始" 如果没有阻塞。

## 额外上下文

[任何与此部分相关的额外观察]
```

创建拆分时：

- **宁可多个薄 issue，不要少数厚 issue** — 每个都应该是可独立修复和验证的
- **诚实标记阻塞关系** — 如果 B 确实需要 A 先修复才能测试，就说明。如果它们独立，双方都标记为 "无 — 可以立即开始"
- **按依赖顺序创建 issue** — 这样你可以在 "被阻塞于" 中引用真实 issue 编号
- **最大化并行度** — 目标是多人（或多代理）可以同时处理不同 issue

#### 所有 issue 正文的规则

- **不要有文件路径或行号** — 这些会过时
- **使用项目的领域语言**（如果有 UBIQUITOUS_LANGUAGE.md 就检查它）
- **描述行为，不是代码** — "同步服务未能应用补丁" 而不是 "applyPatch() 在第 42 行抛出"
- **复现步骤是必须的** — 如果无法确定，询问用户
- **保持简洁** — 开发者应该能在 30 秒内读完

提交后，打印所有 issue URL（附上阻塞关系的摘要），然后问："下一个 issue，还是我们结束了？"

### 5. 继续会话

一直继续到用户说结束为止。每个 issue 是独立的 — 不要批量处理。
