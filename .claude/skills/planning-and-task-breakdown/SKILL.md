# 规划与任务分解

## 概述

将工作分解为带有明确验收标准的小型可验证任务。好的任务分解决定了代理是可靠地完成工作还是产生一团糟。每个任务应足够小，可以在单次专注会话中实现、测试和验证。

## 何时使用

- 你有规格说明，需要将其分解为可实现单元
- 任务感觉太大或太模糊而无法开始
- 工作需要跨多个代理或会话并行化
- 你需要向人传达范围
- 实现顺序不明确

**何时不使用：** 范围明确的单文件变更，或规格说明已包含定义良好的任务。

## 规划过程

### 步骤 1：进入规划模式

在编写任何代码之前，以只读模式操作：

- 阅读规格说明和相关代码库部分
- 识别现有模式和约定
- 映射组件之间的依赖关系
- 记录风险和未知因素

**规划期间不要编写代码。** 输出是计划文档，而非实现。

### 步骤 2：识别依赖图谱

映射依赖关系：

```
数据库 架构
    │
    ├── API 模型/类型
    │       │
    │       ├── API 端点
    │       │       │
    │       │       └── 前端 API 客户端
    │       │               │
    │       │               └── UI 组件
    │       │
    │       └── 验证逻辑
    │
    └── 种子数据 / 迁移
```

实现顺序遵循依赖图谱自底向上：先构建基础。

### 步骤 3：垂直切分

不是先构建所有数据库、再构建所有 API、再构建所有 UI——而是一次构建一个完整的功能路径：

**差（水平切分）：**
```
任务 1：构建完整数据库 架构
任务 2：构建所有 API 端点
任务 3：构建所有 UI 组件
任务 4：连接所有内容
```

**好（垂直切分）：**
```
任务 1：用户可以创建账户（注册的 架构 + API + UI）
任务 2：用户可以登录（认证 架构 + API + UI）
任务 3：用户可以创建任务（任务 架构 + API + UI）
任务 4：用户可以查看任务列表（查询 + API + UI）
```

每个垂直切分交付可工作、可测试的功能。

### 步骤 4：编写任务

每个任务遵循此结构：

```markdown
## 任务 [N]: [简短描述性标题]

**描述：** 一段说明此任务完成什么。

**验收标准：**
- [ ] [具体的、可测试的条件]
- [ ] [具体的、可测试的条件]

**验证：**
- [ ] 测试通过：`npm test -- --grep "feature-name"`
- [ ] 构建成功：`npm run build`
- [ ] 手动检查：[要验证的内容描述]

**依赖：** [此任务依赖的任务编号，或"无"]

**可能触及的文件：**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**预估范围：** [小：1-2 个文件 | 中：3-5 个文件 | 大：5+ 个文件]
```

### 步骤 5：排序和检查点

安排任务使得：

1. 依赖关系满足（先建基础）
2. 每个任务使系统保持工作状态
3. 每 2-3 个任务后设置验证检查点
4. 高风险任务靠前（快速失败）

添加显式检查点：

```markdown
## 检查点：任务 1-3 之后
- [ ] 所有测试通过
- [ ] 应用构建无错误
- [ ] 核心用户流程端到端可用
- [ ] 继续前与人工审查
```
