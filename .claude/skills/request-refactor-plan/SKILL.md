当用户想要创建重构请求时，将触发此技能。你应该遵循以下步骤。如果认为不必要，可以跳过某些步骤。

1. 询问用户关于他们想要解决的问题的详细描述以及任何可能的解决方案想法。

2. 探索代码库以验证他们的断言并理解代码库的当前状态。

3. 询问他们是否考虑过其他选项，并向他们展示备选方案。

4. 深入访谈用户关于实现细节。要极其详细和彻底。

5. 敲定实现的精确范围。确定你计划改变什么和不改变什么。

6. 在代码库中检查该领域的测试覆盖率。如果测试覆盖率不足，询问用户他们的测试计划是什么。

7. 将实现分解为一个逐步提交的计划。记住 Martin Fowler 的建议："让每个重构步骤尽可能小，这样你总能确认程序在运行。"

8. 创建一个包含重构计划的 GitHub issue。使用以下模板作为 issue 描述：

<refactor-plan-template>

## 问题陈述

开发者所面临的问题，从开发者的视角出发。

## 解决方案

问题的解决方案，从开发者的视角出发。

## 提交记录

一份冗长、详细的实施计划。用通俗英语编写计划，将实现分解为尽可能小的提交。每次提交后代码库都应该处于可工作状态。

## 决策文档

做出的实施决策列表。可以包括：

- 将被构建/修改的模块
- 将被修改的模块的接口
- 开发者的技术澄清
- 架构决策
- 架构 变更
- API 契约
- 特定交互

不要包含具体的文件路径或代码片段。它们可能很快就会过时。

## 测试决策

做出的测试决策列表。包括：

- 描述什么是好的测试（只测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似的测试类型）

## 超出范围

描述该重构中超出范围的内容。

## 备注（可选）

有关重构的任何其他备注。

</refactor-plan-template>
