## 目标

在实施前识别三个核心工件（`spec.md`、`plan.md`、`tasks.md`）中的不一致、重复、歧义和未指定项。此命令仅在 `__SPECKIT_COMMAND_TASKS__` 成功生成完整的 `tasks.md` 后才能运行。

## 操作约束

**严格只读**：**不要**修改任何文件。输出结构化的分析报告。提供可选修复计划（用户必须明确批准后才能手动调用后续编辑命令）。

**宪法权威**：项目宪法（`/memory/constitution.md`）在此分析范围内是**不可协商的**。宪法冲突自动标记为严重，需要调整 spec、plan 或 tasks——而非淡化、重新解释或静默忽略原则。如果原则本身需要更改，则必须在 `__SPECKIT_COMMAND_ANALYZE__` 之外的单独、明确的宪法更新中进行。

## 执行步骤

### 1. 初始化分析上下文

从仓库根目录运行一次 `{SCRIPT}` 并解析 JSON 获取 FEATURE_DIR 和 AVAILABLE_DOCS。推导绝对路径：

- SPEC = FEATURE_DIR/spec.md
- PLAN = FEATURE_DIR/plan.md
- TASKS = FEATURE_DIR/tasks.md

如果缺少任何必需文件，则中止并显示错误消息（指示用户运行缺失的前提命令）。
对于参数中的单引号（如 "I'm Groot"），使用转义语法：例如 'I'\''m Groot'（或使用双引号："I'm Groot"）。

### 2. 加载工件（渐进式披露）

从每个工件加载最小必要的上下文：

**从 spec.md：**

- 概述/上下文
- 功能需求
- 成功标准（可衡量的结果——例如性能、安全、可用性、用户成功、业务影响）
- 用户故事
- 边界情况（如果存在）

**从 plan.md：**

- 架构/技术栈选择
- 数据模型引用
- 阶段
- 技术约束

**从 tasks.md：**

- 任务 ID
- 描述
- 阶段分组
- 并行标记 [P]
- 引用的文件路径

**从宪法：**

- 加载 `/memory/constitution.md` 进行原则验证

### 3. 构建语义模型

创建内部表示（不要在输出中包含原始工件）：

- **需求清单**：对于每个功能需求（FR-###）和成功标准（SC-###），记录一个稳定的键。存在显式 FR-/SC- 标识符时将其作为主键，可选地推导一个祈使短语 slug 以提高可读性（例如 "用户可上传文件" → `user-can-upload-file`）。仅包含需要可构建工作的成功标准项（如负载测试基础设施、安全审计工具），排除启动后的结果指标和业务 KPI（如"将支持工单减少 50%"）
- **用户故事/动作清单**：具有验收标准的离散用户操作
- **任务覆盖映射**：将每个任务映射到一个或多个需求或故事（通过关键词/显式引用模式如 ID 或关键短语推断）
- **宪法规则集**：提取原则名称和 MUST/SHOULD 规范声明

### 4. 检测轮次（令牌高效分析）

专注于高信号发现。总计限制为 50 项；其余归入溢出摘要。

#### A. 重复检测

- 识别近似重复的需求
- 标记质量较低的措辞以待合并

#### B. 歧义检测

- 标记缺乏可衡量标准的模糊形容词（快速、可扩展、安全、直观、健壮）
- 标记未解决的占位符（TODO、TKTK、???、`<placeholder>` 等）

#### C. 规范不足

- 有动词但缺少对象或可衡量结果的需求
- 缺少验收标准对齐的用户故事
- 引用 spec/plan 中未定义的文件或组件的任务

#### D. 宪法对齐

- 任何与 MUST 原则冲突的需求或计划元素
- 宪法中缺少的强制章节或质量门

#### E. 覆盖缺口

- 零关联任务的需求
- 无映射需求/故事的任务
- 需要可构建工作但未在任务中反映的成功标准（性能、安全、可用性）

#### F. 不一致

- 术语漂移（同一概念在不同文件中命名不同）
- plan 中引用但 spec 中缺失的数据实体（反之亦然）
- 任务排序矛盾（例如，基础设置任务之前的集成任务没有依赖说明）
- 冲突的需求（例如，一个需要 Next.js 而另一个指定 Vue）

### 5. 严重性分配

使用此启发式方法对发现进行优先级排序：

- **严重**：违反宪法 MUST、缺少核心 spec 工件、或零覆盖且阻塞基线功能的需求
- **高**：重复或冲突的需求、模糊的安全/性能属性、不可测试的验收标准
- **中**：术语漂移、缺少非功能性任务覆盖、边界情况说明不足
- **低**：风格/措辞改进、不影响执行顺序的次要冗余

## 操作原则

### 上下文效率

- **最小高信号令牌**：专注于可操作的发现，而非详尽的文档记录
- **渐进式披露**：增量加载工件；不要将所有内容倾倒到分析中
- **令牌高效输出**：限制发现表为 50 行；汇总溢出部分
- **确定性结果**：无更改重新运行应产生一致的 ID 和计数

### 分析指南

- **绝不修改文件**（此为只读分析）
- **绝不幻觉缺失部分**（如果缺失，准确报告）
- **优先处理宪法违规**（这些始终是严重问题）
- **使用示例而非详尽规则**（引用具体实例，而非通用模式）
- **优雅地报告零问题**（输出带有覆盖统计的成功报告）
