# 代码库设计

设计**深模块**：在小接口背后承载大量行为，放置在干净的接缝处，并通过该接口进行测试。无论在哪里设计或重构代码，都使用这套语言和这些原则。目标是为调用者提供杠杆（leverage），为维护者提供局部性（locality），为所有人提供可测试性。

## 术语表

请准确使用这些术语——不要用"组件（component）""服务（service）""API"或"边界（boundary）"来替代。一致的用词正是这套词汇的意义所在。

**模块（Module）** — 任何拥有接口和实现的东西。刻意地与规模无关：可以是一个函数、类、包，或横跨多层的切片。_避免用_：unit、component、service。

**接口（Interface）** — 调用者为了正确使用模块所必须知道的一切：类型签名，还包括不变量、顺序约束、错误模式、所需的配置以及性能特征。_避免用_：API、signature（过于狭窄——它们仅指类型层面的表面）。

**实现（Implementation）** — 模块内部的东西，它的代码主体。与 **Adapter（适配器）** 有所区别：一个东西可以是小适配器配大实现（一个 Postgres 仓库），也可以是大适配器配小实现（一个内存中的 fake）。当话题是接缝本身时用"adapter"，其他情况用"implementation"。

**深度（Depth）** — 接口层面的杠杆：调用者（或测试）每学习一单位接口所能触发的行为量。当大量行为隐藏在小接口背后时，模块是**深的**；当接口的复杂度几乎与实现相当时，模块是**浅的**。

**接缝（Seam）** _(Michael Feathers)_ — 一个无需在原地编辑就能改变行为的位置；即模块接口所在的*位置*。接缝放在哪里本身就是一个设计决策，与接缝背后放什么内容相互独立。_避免用_：boundary（与 DDD 的限界上下文含义纠缠不清）。

**适配器（Adapter）** — 在某个接缝处满足某个接口的具体事物。描述的是*角色*（它填补哪个槽位），而非实质（里面装的是什么）。

**杠杆（Leverage）** — 调用者从深度中获得的收益：每学习一单位接口获得更多能力。一份实现回报到 N 个调用点和 M 个测试。

**局部性（Locality）** — 维护者从深度中获得的收益：变更、bug、知识和验证集中在一处，而不是散落在各个调用者之间。修一处，处处修复。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 很少实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，问自己：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂度隐藏到内部吗？

## 原则

- **深度是接口的属性，而不是实现的属性。** 深模块内部可以由小型的、可 mock 的、可替换的部件组成——它们只是不属于接口的一部分。模块可以有**内部接缝**（对其实现私有，供其自身测试使用），也有位于接口处的**外部接缝**。
- **删除测试。** 想象删除这个模块。如果复杂度随之消失，它就是个透传层。如果复杂度在 N 个调用者处重新出现，那它就在发挥价值。
- **接口就是测试面。** 调用者和测试跨越的是同一个接缝。如果你想测试接口*之外*的东西，那么这个模块的形状多半设计错了。
- **一个适配器意味着接缝是假设性的；两个适配器才意味着真实接缝。** 除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，而不是自己创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小的表面积。** 方法越少 = 所需测试越少。参数越少 = 测试搭建越简单。

## 关系

- 一个 **Module** 恰好拥有一个 **Interface**（它呈现给调用者和测试的表面）。
- **Depth** 是 **Module** 的属性，相对于其 **Interface** 来衡量。
- **Seam** 是 **Module** 的 **Interface** 所在之处。
- **Adapter** 位于某个 **Seam** 处，满足该 **Interface**。
- **Depth** 为调用者带来 **Leverage**，为维护者带来 **Locality**。

## 被否决的表述

- **把深度定义为实现行数与接口行数之比**（Ousterhout）：会鼓励给实现注水。我们改用"深度即杠杆"的定义。
- **把 "Interface" 当作 TypeScript 的 `interface` 关键字或类的公共方法**：过于狭窄——这里的接口包括调用者必须知道的每一个事实。
- **"Boundary"（边界）**：与 DDD 的限界上下文含义纠缠不清。请说 **seam** 或 **interface**。
