# Prototype（原型）

原型是**用来回答一个问题的用完即弃的代码**。问题决定了原型的形态。

## 选择分支

确定要回答的是哪个问题——从用户的提示、周围的代码中推断，如果用户在场也可以直接询问：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个小型交互式终端应用，将状态机推入那些在纸面上难以推理的场景。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在单个路由上生成多个截然不同的 UI 变体，通过 URL 查询参数和一个浮动底栏进行切换。

这两个分支产出的产物截然不同——选错了会浪费整个原型。如果问题确实模糊且用户无法联系上，默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两个分支共同遵守的规则

1. **从第一天起就是用完即弃的，并明确标注。** 将原型代码放在它实际会被使用的位置附近（紧邻它所对应的模块或页面），以便上下文一目了然——但命名要让随意的读者一眼看出这是原型，而非生产代码。对于用完即弃的 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令即可运行。** 使用项目现有任务运行器支持的任何方式——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够不假思索地启动它。
3. **默认不做持久化。** 状态保存在内存中。持久化恰恰是原型要*检验*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，则使用一个临时数据库或本地文件，并起一个醒目的 "PROTOTYPE — wipe me"（原型——可清除）名称。
4. **跳过打磨。** 不写测试，除了让原型*能跑起来*之外不做错误处理，不做抽象。重点是快速学到东西。
5. **呈现状态。** 每次操作后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户能看到发生了什么变化。
6. **完成后将其留存。** 将任何经过验证的决策融入真实代码，然后将原型本身作为**第一手资料**留存：提交到一个用完即弃的分支上（不在 main 中），并在实现 issue 上留下指向该分支的上下文指针。同时把答案——结论以及它所解决的问题——记录在 issue 或 commit 中。main 分支只保留经过验证的决策。
