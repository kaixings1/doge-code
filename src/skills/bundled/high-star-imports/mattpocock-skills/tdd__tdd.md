# 测试驱动开发（TDD）

TDD 就是红 → 绿的循环。本技能是一份参考手册，让这个循环产出值得保留的测试：什么是好测试、测试写在哪里、反模式有哪些，以及循环的规则。每一节都适用于每一个周期——在进入循环之前和循环进行中查阅它们，而不是事后。

在探索代码库时，请阅读 `CONTEXT.md`（如果存在），以确保测试名称和接口用语与项目的领域语言一致，并尊重你所改动区域中的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底改变；测试不应该变。好测试读起来像一份规格说明——"用户可以使用有效购物车结账"明确告诉你存在什么能力——并且能在重构后依然有效，因为它不关心内部结构。

示例参见 [tests.md](tests.md)，Mock 指南参见 [mocking.md](mocking.md)。

## 缝合点（Seam）——测试写在哪里

**缝合点（seam）** 是你进行测试的公共边界：即在不深入内部的情况下观察行为的接口。测试写在缝合点上，绝不针对内部实现。

**只在预先约定的缝合点上测试。** 在编写任何测试之前，先写下待测试的缝合点并与用户确认。未经确认的缝合点上不写任何测试。你不可能测试所有东西——预先就缝合点达成一致，才能让测试精力落在关键路径和复杂逻辑上，而不是每一个边缘情况上。

要问："公共接口是什么？我们应该测试哪些缝合点？"

## 反模式

- **与实现耦合** —— Mock 内部协作者、测试私有方法，或通过旁路验证（例如直接查询数据库而不是使用接口）。特征：重构时测试挂了，但行为并没有改变。
- **同义反复（Tautological）** —— 断言以与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导出来的快照、断言常量等于它自己），因此它从构造上就会通过，永远不可能与代码产生分歧。期望值必须来自独立的真相来源——一个已知正确的字面量、一个算好的示例、规格说明。
- **水平切分** —— 先写完所有测试，再写完所有实现。批量测试验证的是_想象中_的行为：你测试的是事物的_形状_而非面向用户的行为，测试会对真实变化失去敏感度，而且你在理解实现之前就锁死了测试结构。应该采用**垂直切分**——一个测试 → 一段实现 → 重复，每个测试都是一颗**曳光弹（tracer bullet）**，响应上一个周期带给你的认知。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写恰好能让它通过的代码。不要为未来的测试做预判，也不要添加投机性的功能。
- **一次一个切片。** 每个周期一个缝合点、一个测试、一段最小实现。
- **重构不属于这个循环。** 它属于评审阶段（参见 `code-review` 技能），而不是红 → 绿的实现周期。
