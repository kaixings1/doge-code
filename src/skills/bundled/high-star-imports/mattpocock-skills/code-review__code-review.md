---

对 `HEAD` 与用户提供的固定点之间的 diff 进行双维度审查：

- **规范（Standards）**——代码是否符合本仓库已记录的编码规范？
- **规格（Spec）**——代码是否忠实实现了原始 issue / PRD / 规格说明？

两个维度都作为**并行子代理**运行，以避免互相污染上下文，然后由本技能汇总它们的发现。

issue 跟踪器应当已提供给你——如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户所说的固定点是什么就用什么——commit SHA、分支名、tag、`main`、`HEAD~5` 等。如果用户没有指定，请询问。

一次性确定 diff 命令：`git diff <fixed-point>...HEAD`（三点语法，以便与 merge-base 比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

在继续之前，确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。错误的 ref 或空 diff 应在此处失败——而不是在两个并行子代理内部。

### 2. 确定规格来源

按以下顺序查找原始规格说明：

1. commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD/规格文件。
4. 如果什么都找不到，询问用户规格说明在哪里。如果用户说没有，则**规格（Spec）**子代理将跳过并报告“无可用规格”。

### 3. 确定规范来源

仓库中任何描述代码应如何编写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库已记录的内容之外，规范（Standards）维度始终包含下面的**坏味道基线（smell baseline）**——这是一组固定的 Fowler 代码坏味道（《Refactoring》第 3 章），即使仓库没有任何文档也适用。有两条规则约束它：

- **仓库标准优先。** 已记录的仓库标准总是胜出；当仓库标准认可某做法而基线会标记它时，抑制该坏味道。
- **始终是主观判断。** 每个坏味道都是一个标注式的启发项（“可能是 Feature Envy”），绝不是硬性违规——而且，与本节中的任何标准一样，跳过任何工具已强制执行的内容。

每个坏味道的描述格式为*它是什么* → *如何修复*；将其与 diff 进行对照：

- **Mysterious Name（命名晦涩）**——函数、变量或类型的名称无法揭示其用途或内容。→ 重命名；如果起不出诚实的名字，说明设计本身就不清晰。
- **Duplicated Code（重复代码）**——变更中多个 hunk 或文件出现相同的逻辑形状。→ 提取共享的形状，在两处调用。
- **Feature Envy（依恋情结）**——一个方法访问其他对象的数据多于访问自己的数据。→ 将该方法移到它依恋的数据所属的对象上。
- **Data Clumps（数据泥团）**——同样几个字段或参数总是结伴出现（一个渴望诞生的类型）。→ 将它们打包成一个类型并传递。
- **Primitive Obsession（基本类型偏执）**——用基本类型或字符串代替本应有自己类型的领域概念。→ 为该概念创建一个小的类型。
- **Repeated Switches（重复 switch）**——对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 用多态替换，或让两处共享一个映射。
- **Shotgun Surgery（霰弹式修改）**——一个逻辑变更迫使在 diff 中的许多文件里进行分散编辑。→ 将一起变化的内容聚到一个模块中。
- **Divergent Change（发散式变化）**——一个文件或模块因多个不相关的原因被编辑。→ 拆分它，让每个模块只因一个原因变化。
- **Speculative Generality（夸夸其谈通用性）**——为规格中并不存在的需求而添加的抽象、参数或钩子。→ 删除它；内联回去，直到出现真实需求。
- **Message Chains（过长消息链）**——调用者不应依赖的冗长 `a.b().c().d()` 导航。→ 用第一个对象上的一个方法隐藏这段遍历。
- **Middle Man（中间人）**——几乎只做转发的类或函数。→ 去掉它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）**——忽略或覆盖了大部分继承内容的子类或实现者。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

在一条消息中发送两个 `Agent` 工具调用。两者均使用 `general-purpose` 子代理。

**规范（Standards）子代理提示词**——包含：

- 完整的 diff 命令和 commit 列表。
- 你在第 3 步中找到的规范来源文件列表，**外加第 3 步的坏味道基线全文粘贴进去**——子代理无法以其他方式访问它。
- 任务指令：“报告——在相关处按文件/hunk——(a) diff 违反已记录标准的每一处：引用该标准（文件 + 规则）；(b) 你发现的任何基线坏味道：说出名称并引用该 hunk。区分硬性违规与主观判断——违反已记录标准可能是硬性的，但基线坏味道始终是主观判断，且已记录的仓库标准优先于基线。跳过任何工具已强制执行的内容。400 字以内。”

**规格（Spec）子代理提示词**——包含：

- diff 命令和 commit 列表。
- 规格说明的路径或获取到的内容。
- 任务指令：“报告：(a) 规格要求但缺失或仅部分实现的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现方式有误的需求。每项发现都引用规格中的对应行。400 字以内。”

如果缺少规格说明，跳过规格（Spec）子代理，并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下呈现两份报告，原样或稍作清理。**不要**合并或重新排序发现——两个维度刻意保持分离（见_为什么是两个维度_）。

最后以一行总结收尾：每个维度的发现总数，以及每个维度*内部*最严重的问题（如有）。不要跨维度选出唯一的“冠军”——那正是这种分离所要防止的重新排序行为。

## 为什么是两个维度

一个变更可能通过一个维度而未通过另一个维度：

- 完全遵循每一条标准但实现了错误内容的代码 → **规范通过，规格未通过。**
- 完全做到了 issue 所要求的内容但破坏了项目约定的代码 → **规格通过，规范未通过。**

分开报告可以避免一个维度掩盖另一个维度。
