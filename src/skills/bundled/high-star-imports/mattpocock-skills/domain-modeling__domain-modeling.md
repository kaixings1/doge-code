# 领域建模

在设计过程中，主动构建并打磨项目的领域模型。这是一种*主动*的纪律——挑战术语、构思边界情况场景，并在术语和决策一旦成型时就立即写入词汇表和决策记录。（仅仅是*阅读* `CONTEXT.md` 中的词汇并不属于本技能——那是一行代码的习惯，任何技能都能做到。本技能适用于你在*改变*模型之时，而不仅仅是消费它。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录下存在 `CONTEXT-MAP.md`，则该仓库有多个上下文。该映射文件指向每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定的决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件——只在有内容要写时才创建。如果尚不存在 `CONTEXT.md`，则在第一个术语确定时创建它。如果尚不存在 `docs/adr/`，则在需要第一个 ADR 时创建它。

## 会话过程中

### 对照词汇表进行挑战

当用户使用的术语与 `CONTEXT.md` 中已有的语言冲突时，立即指出。"你的词汇表将 'cancellation' 定义为 X，但你似乎指的是 Y——到底是哪个？"

### 打磨模糊的语言

当用户使用模糊或多义的术语时，提出一个精确的规范术语。"你说的是 'account'——你指的是 Customer 还是 User？这是两个不同的东西。"

### 讨论具体场景

在讨论领域关系时，用具体场景对它们进行压力测试。构思能够探查边界情况、迫使用户对概念之间的边界做出精确表述的场景。

### 与代码交叉验证

当用户陈述某事物如何运作时，检查代码是否与其一致。如果发现矛盾，将其呈现出来："你的代码会取消整个 Order，但你刚才说部分取消是可能的——哪个是对的？"

### 即时更新 CONTEXT.md

当一个术语确定下来时，当场更新 `CONTEXT.md`。不要攒着批量处理——要随时记录。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应当完全不含实现细节。不要把 `CONTEXT.md` 当作规格说明、草稿本或实现决策的存放处。它只是词汇表，仅此而已。

### 谨慎提供 ADR

只有当以下三点全部满足时，才提议创建 ADR：

1. **难以逆转**——日后改变主意的代价是可观的
2. **缺乏上下文会令人费解**——未来的读者会疑惑"他们为什么这样做？"
3. **是真实权衡的结果**——确实存在其他备选方案，而你基于特定理由选择了其中之一

如果三者中缺少任何一点，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
