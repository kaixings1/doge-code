# Triage（分诊）

将项目 issue 跟踪器上的 issue 通过一个由分诊角色组成的小型状态机进行流转。

如果本仓库将外部 pull request 视为请求入口（参见 issue 跟踪器配置），分诊也覆盖它们：**PR 就是附带了代码的 issue**——相同的角色、相同的状态、相同的状态机，仅在下文以"针对 PR"标注了少数差异。根据跟踪器配置，将裸引用的 `#42` 解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器上的每条评论或 issue **必须**以下面这行免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何撰写持久可用的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**角色：

- `bug` — 某处出现了故障
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 已完整说明，可交给 AFK agent 处理
- `ready-for-human` — 需要人类实现
- `wontfix` — 不会采取行动

针对 PR，同样的状态是对附带代码的描述：`ready-for-agent` 表示已附带简报，agent 应对 diff 采取下一步行动；`ready-for-human` 表示可以由人类合并。

每个已分诊的 issue 应当恰好携带一个类别角色和一个状态角色。如果状态角色之间存在冲突，请先标记出来并询问维护者，然后再做其他事情。

这些是规范的角色名称——issue 跟踪器中实际使用的标签字符串可能不同。映射关系应当已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

状态流转：一个没有标签的 issue 通常先进入 `needs-triage`；再从那里流转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 会回到 `needs-triage`。维护者可以随时覆盖——对看起来异常的流转要标记出来并在继续之前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。理解请求并行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的内容

查询 issue 跟踪器并呈现三个分组，最旧的在前：

1. **无标签** — 从未分诊过。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且自上次分诊记录以来报告者有活动** — 需要重新评估。

当 PR 在范围内时，将这些分组中纳入外部 PR，并在每行标注 `[PR]` 或 `[issue]`。发现环节仅展示*外部* PR（跟踪器配置定义了谁算外部）——协作者进行中的 PR 不属于分诊工作。此过滤仅用于发现环节；被明确点名提及的 PR 无论作者是谁都会被分诊。

展示每项的数量和一行摘要。让维护者选择。

## 分诊特定的 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR 还包括 diff）。解析任何先前的分诊记录，避免重复询问已解决的问题。使用项目的领域术语表探索代码库，并遵守该区域的 ADR。对代码库运行两项检查：(a) **冗余检查** —— 按领域概念（而非仅按请求措辞）搜索所请求行为是否已有实现，并报告你查看了哪些地方。如果找到了，它就是一个"已实现"的 `wontfix`（步骤 5）。(b) **先前拒绝** —— 阅读 `.out-of-scope/*.md`，找出任何与此请求相似的条目。

2. **给出建议。** 告诉维护者你的类别和状态建议及理由，并附上与请求相关的简短代码库摘要——包括该功能是否已经实现。等待指示。

3. **验证主张。** 在任何深度追问之前，先检查该主张是否站得住脚。对于 bug，按照报告者的步骤复现它。对于 PR，确认 diff 确实实现了其声称的功能——检出它，运行相关的测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（这是很强的 `needs-info` 信号）。经过确认的验证能写出强得多的 agent 简报。

4. **深度追问（如需要）。** 如果请求需要进一步充实，同时运行 `/grilling` 和 `/domain-modeling` 技能——一次一个问题地将其打磨成型，在决策落定时同步更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发布一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 结构与 agent 简报相同，但要说明为何无法委派（需要主观判断、外部访问、设计决策、手动测试）。
   - `needs-info` — 发布分诊记录（模板见下文）。
   - `wontfix` — 关闭，评论内容取决于*原因*：
     - **已实现** — 该变更已存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝的*请求，而不是已实现的）。
     - **拒绝（bug）** — 礼貌地解释，然后关闭。
     - **拒绝（enhancement）** — 写入 `.out-of-scope/`，在评论中链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用该角色。如有部分进展可选择性评论。

## 快速状态覆盖

如果维护者说"move #42 to ready-for-agent"，信任他们并直接应用该角色。确认你即将执行的操作（角色变更、评论、关闭），然后行动。跳过深度追问。如果在没有进行追问会话的情况下移至 `ready-for-agent`，询问他们是否想撰写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

将追问过程中解决的所有内容记录在"established so far"之下，以免工作成果丢失。问题必须具体且可执行，而不是"请提供更多信息"。

## 恢复先前的会话

如果 issue 或 PR 上已存在先前的分诊记录，阅读它们，检查报告者是否已回答任何待解决的问题，并在继续之前呈现更新后的情况。不要重复询问已解决的问题。
