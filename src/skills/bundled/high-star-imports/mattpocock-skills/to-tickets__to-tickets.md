# To Tickets

将计划、规格说明或对话拆解为一组**工单**——曳光弹式的垂直切片，每张工单声明哪些工单**阻塞**它。

问题追踪器和分诊标签词汇表应该已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容开展工作。如果用户以参数形式传入了引用（规格说明路径、问题编号或 URL），请获取并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索代码库，请先探索以了解代码的现状。工单的标题和描述应使用项目的领域词汇表，并遵守你所涉及领域的 ADR。

寻找可以通过预先重构（prefactor）来简化实现的机会。"先让变更变容易，再进行这个容易的变更。"

### 3. 起草垂直切片

将工作拆分为**曳光弹**式工单。

<vertical-slice-rules>

- 每个切片穿过每一层（schema、API、UI、测试），切出一条狭窄但完整的路径——是垂直的，而不是单层的水平切片
- 完成的切片本身即可演示或验证
- 每个切片的大小应能容纳在一个全新的上下文窗口中
- 任何预先重构都应最先完成

</vertical-slice-rules>

为每张工单指定其**阻塞边**——即在它开始之前必须完成的其他工单。没有阻塞者的工单可以立即开始。

**大范围重构是垂直切片的例外。****大范围重构**是指一次机械性变更——重命名一列、重新定义共享符号的类型——其**影响范围**波及整个代码库，一次编辑就会同时破坏数千个调用点，任何垂直切片都无法保持绿色通过。不要强行将其做成曳光弹；而是按**扩张–收缩**模式排序。首先扩张：在旧形式旁边添加新形式，确保不破坏任何东西。然后按影响范围确定批量大小（按包、按目录），分批迁移调用点，每批作为一张独立工单，被扩张工单阻塞；由于旧形式仍然存在，CI 可以逐批保持绿色。最后收缩：当没有调用者残留时，在一张被所有迁移批次阻塞的工单中删除旧形式。即使各批次单独也无法保持绿色时，仍保持该顺序，但让它们共享一个集成分支，所有批次都阻塞在最后一张集成并验证的工单上——只有在那里才承诺绿色通过。

### 4. 向用户提问

将提议的拆解方案以编号列表的形式呈现。对每张工单，展示：

- **标题**：简短的描述性名称
- **被阻塞于**：哪些其他工单（如有）必须先完成
- **交付内容**：这张工单实现端到端工作后的行为

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确——每张工单是否只依赖于真正对它构成门槛的工单？
- 是否有工单需要合并或进一步拆分？

反复迭代，直到用户批准该拆解方案。

### 5. 将工单发布到已配置的追踪器

发布已批准的工单。**如何发布**取决于 `/setup-matt-pocock-skills` 配置的追踪器——两种方式下工单内容相同，只是阻塞边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张工单写一个文件，从 `01` 开始按依赖顺序编号（阻塞者在前）。每个文件的"Blocked by"列出它所依赖的编号/标题。使用下方的单张工单文件模板——每张工单一文件，绝不合并为单个文件。
- **真实问题追踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞者在前）为每张工单发布一个 issue，使每张工单的阻塞边可以引用真实标识符。平台若有原生的阻塞 / 子 issue 关系则使用之；否则将每张工单的"Blocked by"设为阻塞它的 issue。除非另有指示，打上 `ready-for-agent` 分诊标签——这些工单从构造上就是可供 agent 认领的。

处理**前沿**：即所有阻塞者均已完成的所有工单。对于纯线性链条，这意味着从头到尾依次处理。

不要关闭或修改任何父 issue。
