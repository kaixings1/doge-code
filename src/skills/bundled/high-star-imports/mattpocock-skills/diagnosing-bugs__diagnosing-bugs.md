# 诊断 Bug

这是一套针对疑难 bug 的纪律。只有在有明确理由时才可跳过某个阶段。

在探索代码库时，阅读 `CONTEXT.md`（如果存在）以建立对相关模块的清晰心智模型，并查看你所触及领域的 ADR。

## 阶段 1 — 构建反馈循环

**这就是本技能的核心。** 其余一切都是机械操作。如果你有一个**紧凑的**针对该 bug 的通过/失败信号——一个在 _这个_ bug 上会变红的信号——你就能找到原因；二分法、假设检验和插桩都只是在消费这个信号。如果你没有这个信号，盯着代码看多久都没用。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

### 构建反馈循环的方法 —— 大致按此顺序尝试

1. **失败的测试**，在任何能触及该 bug 的接缝处——单元、集成、e2e。
2. **Curl / HTTP 脚本**，针对运行中的开发服务器。
3. **CLI 调用**，使用固定输入，将 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/控制台/网络做断言。
5. **重放捕获的 trace。** 将真实的网络请求/载荷/事件日志保存到磁盘；在隔离环境中通过代码路径重放它。
6. **一次性测试架。** 启动系统的最小子集（一个服务，mock 依赖），用一个函数调用来触发 bug 的代码路径。
7. **属性 / 模糊测试循环。** 如果 bug 是“有时输出错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分测试架。** 如果 bug 出现在两个已知状态（提交、数据集、版本）之间，将“在状态 X 启动、检查、重复”自动化，这样你可以用 `git bisect run` 来运行它。
9. **差分循环。** 将相同输入分别通过旧版本和新版本（或两种配置）运行，并 diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人点击操作，用 `scripts/hitl-loop.template.sh` 驱动 _人_，让循环依然保持结构化。捕获的输出会反馈给你。

构建正确的反馈循环，bug 就已修复了 90%。

### 收紧循环

把循环当作一个产品来对待。一旦你有了 _一个_ 循环，就要**收紧**它：

- 我能让它更快吗？（缓存设置，跳过无关的初始化，缩小测试范围。）
- 我能让信号更锐利吗？（对具体症状做断言，而不是“没有崩溃”。）
- 我能让它更确定吗？（固定时间，固定 RNG 种子，隔离文件系统，冻结网络。）

一个 30 秒且不稳定的循环几乎和不没有循环一样糟；一个 2 秒且确定的循环才算紧凑——这是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。将触发条件循环 100 次，并行化，增加压力，缩小时间窗口，注入 sleep。50% 概率复现的 bug 是可调试的；1% 则不是——不断提高复现率，直到它可调试为止。

### 当你确实无法构建循环时

停下来，明确地说明这一点。列出你尝试过的方法。向用户请求：(a) 访问能复现该问题的环境，(b) 一份捕获的产物（HAR 文件、日志转储、core dump、带时间戳的屏幕录制），或 (c) 允许添加临时生产环境插桩。在**没有**循环的情况下，**不要**继续进行假设。

### 完成标准 —— 一个能变红的紧凑循环

当循环**紧凑**且**能变红**时，阶段 1 即完成：你能说出**一条命令**——一个脚本路径、一次测试调用、一条 curl——并且你**已经至少运行过一次**（粘贴调用及其输出），且该命令：

- [ ] **能变红** —— 它驱动实际的 bug 代码路径，并对**用户的确切症状**做断言，因此它能在这个 bug 上变红，修复后变绿。不是“运行不出错”——它必须能够_捕获这个特定的 bug_。
- [ ] **确定性** —— 每次运行的结论都相同（不稳定 bug：有固定的、高的复现率，如上所述）。
- [ ] **快速** —— 以秒计，而不是以分钟计。
- [ ] **Agent 可运行** —— 你可以无人值守地运行它；人只在通过 `scripts/hitl-loop.template.sh` 时才参与循环。

如果你发现自己在该命令存在之前就读代码来构建理论，**停下——直接跳到假设正是本技能要防止的失败。**没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。看它变红——bug 出现了。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——而不是碰巧发生在附近的其他失败。错误的 bug = 错误的修复。
- [ ] 该失败在多次运行中可复现（或者，对于非确定性 bug，复现率高到足以进行调试）。
- [ ] 你已捕获确切的症状（错误消息、错误输出、缓慢的耗时），以便后续阶段可以验证修复是否真正解决了它。

### 最小化

一旦它变红，将复现场景缩减到**仍会变红的最小场景**。**一次一个**地削减输入、调用方、配置、数据和步骤，每次削减后重新运行循环——只保留对失败起承重作用的部分。

为什么要费这个劲：最小化复现可以缩小阶段 3 的假设空间（需要怀疑的活动部件更少），并成为阶段 5 中干净的回归测试。

当**每个剩余元素都是承重的**时即完成——移除其中任何一个都会使循环变绿。

在复现**并且**最小化完成之前，不要继续。

## 阶段 3 — 提出假设

在测试任何假设之前，生成 **3–5 个按优先级排序的假设**。单一假设的生成会锚定在第一个看似合理的想法上。

每个假设都必须是**可证伪的**：陈述它做出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 将使 bug 消失 / <改变 Z> 将使它更严重。”

如果你无法陈述预测，这个假设只是一种感觉——丢弃它或将其锐化。

**在测试之前，将排好序的列表展示给用户。**他们通常拥有能立即重新排序的领域知识（“我们刚刚部署了对 #3 的更改”），或者知道他们已经排除的假设。这个检查点成本很低，却节省大量时间。不要因此阻塞——如果用户不在，就按你的排序继续。

## 阶段 4 — 插桩

每次探测必须对应阶段 3 中的某个具体预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. 在能区分各假设的边界处打**定向日志**。
3. 永远不要“记录所有内容然后 grep”。

**给每条调试日志打上**唯一前缀标签，例如 `[DEBUG-a4f2]`。这样最后清理时只需一次 grep。未打标签的日志会残留；打了标签的日志会被清除。

**性能分支。**对于性能回归，日志通常是错误的方法。取而代之：建立基线测量（计时测试架、`performance.now()`、分析器、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

在修复**之前**编写回归测试——但前提是存在**正确的接缝**。

正确的接缝是指测试在调用点以其真实发生方式 exercising **真实的 bug 模式**的接缝。如果唯一可用的接缝太浅（bug 需要多个调用方时却只有单调用方测试，单元测试无法复现触发 bug 的调用链），那么在那里写回归测试只会带来虚假的信心。

**如果不存在正确的接缝，这本身就是一项发现。**记录下来。代码库的架构正在阻碍对这个 bug 的锁定。将此标记给下一个阶段。

如果存在正确的接缝：

1. 将最小化复现转化为该接缝处的失败测试。
2. 看它失败。
3. 应用修复。
4. 看它通过。
5. 针对原始（未最小化）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 复盘

宣布完成前必须完成：

- [ ] 原始复现场景不再复现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录不存在接缝）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（用前缀 `grep`）
- [ ] 一次性原型已删除（或移动到明确标记的调试位置）
- [ ] 结果被证明正确的假设已写进 commit / PR 消息——以便下一个调试者学习

**然后问：什么本可以预防这个 bug？**如果答案涉及架构层面的改变（没有好的测试接缝、调用方纠缠、隐藏耦合），将具体细节移交给 `/improve-codebase-architecture` 技能。在修复**完成之后**提出建议，而不是之前——比起开始时，你现在掌握的信息更多了。
