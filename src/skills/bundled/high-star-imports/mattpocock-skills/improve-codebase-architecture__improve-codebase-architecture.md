# 改进代码库架构

发现架构上的摩擦点，并提出**深化机会**——将浅模块转化为深模块的重构。目标是可测试性和 AI 可导航性。

此命令_参考_项目的领域模型，并建立在一套共享的设计词汇之上：

- 运行 `/codebase-design` 技能以获取架构词汇（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除测试、"接口即测试面"、"一个 adapter = 假想的 seam，两个 = 真实的"）。在每一条建议中都精确使用这些术语——不要漂移到"组件"、"服务"、"API"或"边界"之类的说法。
- `CONTEXT.md` 中的领域语言为良好的 seam 命名；`docs/adr/` 中的 ADR 记录了此命令不应重新争论的决策。

## 流程

### 1. 探索

首先阅读项目的领域词汇表（`CONTEXT.md`）以及你所涉及区域的任何 ADR。

然后使用 Agent 工具并指定 `subagent_type=Explore` 来走查代码库。不要遵循僵化的启发式规则——有机地探索，并记录下你感受到摩擦的地方：

- 哪些地方理解一个概念需要在许多小模块之间来回跳转？
- 哪些模块是**浅的**——接口的复杂度几乎与实现相当？
- 哪些地方仅仅为了可测试性而提取了纯函数，但真正的 bug 却隐藏在它们的调用方式中（没有 **locality**）？
- 哪些紧耦合的模块在其 seam 之间发生泄漏？
- 代码库的哪些部分未被测试，或者难以通过其当前接口进行测试？

对你怀疑是浅的任何东西应用**删除测试**：删除它会集中复杂度，还是仅仅转移它？"是的，会集中"才是你想要的信号。

### 2. 以 HTML 报告的形式呈现候选方案

将一个自包含的 HTML 文件写入操作系统临时目录，确保没有任何东西落入仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，使每次运行都获得一个新文件。为用户打开它——Linux 上 `xdg-open <path>`，macOS 上 `open <path>`，Windows 上 `start <path>`——并告知他们绝对路径。

报告使用 **Tailwind via CDN** 进行布局和样式设计，并在图形/流程/时序能够可靠传达结构时使用 **Mermaid via CDN** 绘制图表。将 Mermaid 与手工制作的 CSS/SVG 视觉效果混合使用——当关系呈图状时（调用图、依赖关系、时序）使用 Mermaid，当你想要更具编辑风格的东西（质量图、剖面图、坍缩动画）时使用手工构建的 div/SVG。每个候选方案都有一个**前后对比可视化**。要注重视觉呈现。

对于每个候选方案，渲染一张卡片，包含：

- **Files** —— 涉及哪些文件/模块
- **Problem** —— 为什么当前架构会造成摩擦
- **Solution** —— 用通俗语言描述将要改变的内容
- **Benefits** —— 从 locality 和 leverage 的角度解释，以及测试将如何改善
- **Before / After diagram** —— 并排对比、自定义绘制，展示浅薄之处和深化效果
- **Recommendation strength** —— `Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽章

报告以**首要推荐**部分结尾：你会首先解决哪个候选方案，以及为什么。

**领域使用 CONTEXT.md 的词汇，架构使用 `/codebase-design` 的词汇。** 如果 `CONTEXT.md` 定义了 "Order"，那就谈"Order 接入模块"——而不是"FooBarHandler"，也不是"Order 服务"。

**ADR 冲突**：如果某个候选方案与现有 ADR 相矛盾，只有当摩擦足够真实、值得重新审视该 ADR 时才呈现它。在卡片中清晰地标记出来（例如一个警告提示框：_"与 ADR-0007 相矛盾——但值得重新开启，因为……"_）。不要列出 ADR 禁止的每一个理论上的重构。

完整的 HTML 骨架、图表模式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

目前先不要提出接口。文件写好之后，询问用户："你想探索其中哪一个？"

### 3. 拷问循环

一旦用户选定了一个候选方案，运行 `/grilling` 技能，与他们一起走查设计树——约束条件、依赖关系、深化后模块的形态、seam 背后是什么、哪些测试得以保留。

随着决策逐渐清晰，副作用会内联发生——运行 `/domain-modeling` 技能，随时保持领域模型最新：

- **想用 `CONTEXT.md` 中不存在的概念命名深化后的模块？** 将该术语添加到 `CONTEXT.md`。如果文件不存在则惰性创建。
- **在对话中锐化了一个模糊的术语？** 立即更新 `CONTEXT.md`。
- **用户以一个承重的理由拒绝了候选方案？** 提议记录一条 ADR，措辞为：_"要我把这个记录为 ADR，以便未来的架构评审不再重复建议它吗？"_ 只有当未来的探索者确实需要这个理由来避免重复建议同样的东西时才提议——跳过临时性的理由（"现在不值得"）和不言自明的理由。
- **想为深化后的模块探索替代接口？** 运行 `/codebase-design` 技能，使用其 design-it-twice 并行子代理模式。
