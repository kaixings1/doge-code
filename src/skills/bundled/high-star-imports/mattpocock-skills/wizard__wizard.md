# Wizard

**Wizard（向导）**是一个 bash 脚本，它一步步引导人工完成一个手动操作繁琐、且每次向 AI 重新解释也很麻烦的流程。它会打开每个 URL，明确说明要点击和复制什么，捕获这些值，并把它们写到该写的地方（`.env`、GitHub secrets），在每个阶段都进行确认，并显示还剩多少步骤。它可能会配置第三方服务、运行一次性迁移，或者将项目从一种状态转换到另一种状态。

令人愉悦的 UX 已经由 [template.sh](template.sh) 解决了——带剩余时间的进度显示、确认门、跨平台 URL 打开（包括 WSL）、隐藏式 secret 输入、幂等的 `.env` upsert、`gh secret`/`gh variable` 写入，以及结束时的总结。**你的职责只是划定流程范围并编写各个阶段。** `STAGES` 标记之上的库在每个 wizard 中都是完全相同的；这种一致性正是关键所在——绝不要手动编辑它。

Wizard 默认是一次性的——为一次运行而构建，保存到临时路径或 `scripts/` 路径，任务完成后删除。只有当用户希望有一个应存放在仓库中的可重复执行路径时，才将其提交。

## 流程

### 1. 划定流程范围

梳理人工必须执行的每个手动步骤，以及在此过程中要捕获的每个值。先阅读仓库——不要一上来就提问：

- 对于配置类任务：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每个 `secrets.*` / `vars.*` 引用都是 wizard 必须产出的值）。
- 对于迁移或状态转换：当前状态、目标状态，以及两者之间的不可逆操作。

然后向用户展示按顺序排列的阶段列表以及每个阶段产出的值，并确认——他们可能会增删或重新排序。

**完成的标志：** 每个阶段都已按顺序命名，并且对于每个捕获的值，你都清楚：(a) 人工从哪里获取它，(b) 它被写入哪里（`.env`、GitHub secret、两者都有，或者都不写——有些阶段是纯操作），以及 (c) 它是 secret（隐藏输入）还是公开的。

### 2. 规划每个阶段的路径

对于每个阶段，写出人工遵循的精确路径：打开哪个 URL、在那里做什么、值在哪里显示、它填入哪个变量——例如"Dashboard → Developers → API keys → Reveal test key → copy"。在你并不真正了解当前 UI 或确切命令时，如实说明，并询问用户或查阅文档——绝不要编造可能不存在的步骤。

**完成的标志：** 每个阶段都能追溯到陌生人也能照着做的具体操作说明。

### 3. 编写 wizard

将 `template.sh` 复制到目标路径。用依赖顺序的 `stage` 替换示例阶段，每个步骤一个。使用库的辅助函数——`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`——并将 `TOTAL_STAGES` 和 `TOTAL_MINUTES` 设为诚实的估计值（这会驱动剩余时间的显示）。

保持模板设定的标准：在请求值之前先打开 URL，任何 secret 都使用 `ask_secret`，每个持久化的值都用 `write_env`，只对 CI 真正需要的值使用 `set_secret`，并在任何不可逆操作之前使用 `confirm`。每个 `stage` 都会清屏，因此只有当前步骤可见——保持每个阶段只做一件聚焦的任务，这样人工需要的信息不会滚出屏幕。不要触碰标记之上的库。

### 4. 验证并交付

- 执行 `bash -n <script>`；如果可用，运行 `shellcheck`。
- 执行 `chmod +x <script>`。
- 不要自己端到端运行它——它会打开浏览器并阻塞在人工输入上。改为静态走查：第 1 步中的每个值都被捕获，并落在第 1 步所说的位置，且每个 `set_secret` 的名称与 CI 中的 `secrets.*` 引用完全匹配。
- 告诉用户如何运行它。如果它是一个可重复执行的路径，将其提交并从 README 链接，这样下一个人就会运行该脚本，而不是去问 AI。
