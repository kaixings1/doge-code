# Ask Matt

你不可能记住每一个技能，所以尽管来问。

一个**流程**是一条贯穿各技能的路径。大多数路径沿着一条**主流程**运行，两条**入口通道**汇入其中。其余的要么是独立的，要么是运行在底层的词汇层。

## 主流程：想法 → 交付

大多数工作所走的路线。你有一个想法，想把它构建出来。

1. **`/grill-with-docs`** —— 通过访谈来打磨想法。当你**拥有一个代码库**时从这里开始：它是有状态的，会把它学到的东西保留在 `CONTEXT.md` 和 ADR 中。（没有代码库？用 `/grill-me` —— 见独立技能。两者都运行同一个 `/grilling` 原语；`grill-with-docs` 是那个会留下书面记录的。）
2. **分支 —— 你能在对话中解决所有问题吗？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、必须亲眼看到的 UI），就绕道做一个原型，用 **`/handoff`** 在两个方向上搭桥（见跨会话）：
   - **`/handoff`** 导出，然后针对该文件打开一个新会话，
   - **`/prototype`** 用一次性代码回答那个问题，
   - 把你学到的东西 **`/handoff`** 回来，并在原始的想法线程中引用它。
3. **分支 —— 这是一个多会话的构建吗？**
   - **是** → **`/to-spec`**（把线程变成规格说明），然后 **`/to-tickets`** 把它拆分为 tracer-bullet 式的工单，每个工单声明其**阻塞边**。在本地追踪器上，这是 `.scratch/<feature>/issues/` 下每个工单一个文件，手动优先处理未被阻塞的；在真正的追踪器上，这些边会变成原生的阻塞链接，因此任何阻塞项已完成的工单都可以被认领 —— 每个工单启动一次 **`/implement`**，**每次之间清空上下文**。
   - **否** → 直接在同一个上下文窗口中运行 **`/implement`**。

   无论哪种方式，**`/implement`** 都会通过在内部驱动 **`/tdd`** 来构建每个 issue —— 一次一个红-绿切片 —— 然后在提交前以 **`/code-review`** 收尾，即对 diff 进行双轴审查（标准 + 规格）。当你只想在没有完整规格的情况下以测试先行的方式构建一个具体行为时，可以单独使用 **`/tdd`**；任何时候你想针对一个固定基准审查分支或 PR 时，可以单独使用 **`/code-review`**。

### 上下文卫生

把第 1–3 步保持在**一个不间断的上下文窗口**中 —— 在 `/to-tickets` 之前不要压缩或清空 —— 这样访谈、规格和工单都建立在同一段思考之上。然后每个 `/implement` 都从全新状态开始，以工单为工作依据。

这个限制就是**[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart zone)**：模型仍能敏锐推理的窗口（在最先进的模型上约为 120k token）。如果某个会话在 `/to-tickets` 之前就接近了这个界限，不要在性能退化状态下硬撑 —— `/handoff` 然后在新线程中继续。

## 入口通道

会产生工作、然后汇入主流程的起始场景。

- **Bug 和请求堆积如山** → **`/triage`**。它让 issue 在分诊角色间流转，产出 agent 可用的 issue，之后由 **`/implement`** 接手。

  分诊只适用于**不是你自己创建的** issue —— bug 报告、传入的功能请求，任何以原始形态到来的东西。`/to-tickets` 产出的工单已经是 agent 可用的，所以**不要对它们做分诊**。

- **出了故障** → **`/diagnosing-bugs`**。针对那些难缠的：第一眼看不出来的 bug、间歇性的 flake、在两个已知良好状态之间悄然潜入的回归。在拥有**紧凑反馈回路**之前，它拒绝建立理论 —— 即一条在*当前*这个 bug 上已经会变红的命令 —— 然后带着回归测试进行修复。当它的复盘发现真正的问题是缺乏锁定 bug 的良好接缝时，会移交给 **`/improve-codebase-architecture`**。

- **一项庞大而迷雾重重的工程 —— 从零开始的项目或大型特性构建，大到无法在一个会话中完成** → **`/wayfinder`**。当从这里到目的地的路还看不清时，它会在 issue 追踪器上绘制一张**共享地图**，列出调查工单，然后逐个解决 —— 产出的是**决策，而非交付物** —— 直到迷雾被推开、道路清晰。然后它在 **`/to-spec`** 处汇入主流程（或者，如果这项工程实际上足够小，就直接进入 **`/implement`**）。**`/grill-with-docs`** 打磨的是一个会话就能容纳的想法，而 wayfinder 面向的是你容纳不下的想法。

## 代码库健康

不是特性开发 —— 而是维护。

- **`/improve-codebase-architecture`** —— 每当你有片刻空闲就运行它，让代码库保持适合 agent 运作的状态。它会浮现出**深化机会**；选定一个就*产生了一个想法*，你可以带着它进入 `/grill-with-docs` 的主流程。它是找出候选者的勘测工具；**`/codebase-design`**（见下文）则是你设计选定方案的工作台。

## 底层词汇

两个由模型调用的参考技能，运行在*其他技能之下* —— 各自是其词汇的唯一事实来源。当问题出在**词汇**而非流程上时直接调用它们；或者让上面的技能自行引入。

- **`/domain-modeling`** —— 打磨项目的*领域*语言：挑战模糊的术语，解决一个 overloaded 的词（"account" 同时干着三份活），把难以逆转的决策记录为 ADR。这是 `/grill-with-docs` 所驱动的主动纪律，让 `CONTEXT.md` 保持为一份干净的术语表。
- **`/codebase-design`** —— deep-module 词汇（module、interface、depth、seam、adapter、leverage、locality），用于设计模块的*形状*：在干净的接缝处，用小接口隐藏大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用它。

## 跨会话

- **`/handoff`** —— 当一个线程已满，或者你需要分叉出去（例如进入一个 `/prototype` 会话）时，它把对话压缩成一个 markdown 文件。你不会在原地继续 —— 你会**打开一个新会话并引用那个文件**来携带上下文跨越过去。它是上下文窗口之间的桥梁，双向皆可。当你想要一个**全新会话**但又需要**保留当前对话**时使用它。
- **`/compact`**（内置）—— 留在**同一对话**中，让前面的轮次被摘要化。在**阶段之间有意识的断点**处使用它，此时你不介意丢失逐字记录的历史。不要在阶段中途压缩 —— agent 可能迷失方向。`/handoff` 是分叉；`/compact` 是继续。

## 独立技能

完全脱离主流程。

- **`/grill-me`** —— 与 `/grill-with-docs` 同样的毫不留情的访谈，但适用于你**没有代码库**的情况。无状态：它不在本地保存任何东西，不构建 `CONTEXT.md`。当你想打磨任何不居于仓库中的计划或设计时使用它。
- **`/prototype`** —— 一个小型的一次性程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。从第一天起就是一次性的 —— 留下答案，删掉代码。它是主流程第 2 步中的绕道，但任何时候当设计问题难以在纸面上敲定时，都可以用它。
- **`/research`** —— 把阅读跑腿的活委派给**后台 agent**：它针对**一手来源**调查一个问题，然后在仓库中留下一个带引用的 Markdown 文件。在它阅读的同时你可以继续工作。它产出的文件是带你*进入*主流程 `/grill-with-docs` 的东西 —— 研究为思考提供养料，而不是取代思考。
- **`/teach`** —— 跨多个会话学习一个概念，把当前目录用作有状态的工作区。
- **`/writing-great-skills`** —— 编写和编辑技能的参考指南。

## 前置条件

**`/setup-matt-pocock-skills`** —— 在你的第一个工程流程之前运行，以配置其他技能所假定的 issue 追踪器、分诊标签和文档布局。自定义的 issue 追踪器也支持。
