---

当用户想要创建重构请求时，将调用此技能。你需要按照以下步骤进行操作。如果你认为某些步骤没有必要，可以跳过。

1. 请用户对其想要解决的问题以及任何潜在的解决方案思路提供一份冗长、详细的描述。

2. 探索仓库，以验证用户的说法并了解代码库的当前状态。

3. 询问他们是否考虑过其他方案，并向他们展示其他可选方案。

4. 就实现细节对用户进行访谈。要极其详细和彻底。

5. 敲定实现的确切范围。明确你计划更改的内容和不计划更改的内容。

6. 在代码库中查看该区域代码的测试覆盖率。如果测试覆盖率不足，请询问用户的测试计划。

7. 将实现拆分为一系列微小提交的计划。记住 Martin Fowler 的建议："让每个重构步骤尽可能小，以便你始终能看到程序处于可运行状态。"

8. 创建一个包含重构计划的 GitHub issue。issue 描述请使用以下模板：

<refactor-plan-template>

## Problem Statement

开发者所面临的问题，从开发者的视角来描述。

## Solution

问题的解决方案，从开发者的视角来描述。

## Commits

一份冗长、详细的实现计划。用平实的语言撰写计划，将实现拆分为尽可能微小的提交。每个提交都应使代码库保持在可运行状态。

## Decision Document

已做出的实现决策的列表。可以包括：

- 将要构建/修改的模块
- 这些模块中将要修改的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体的交互行为

不要包含具体的文件路径或代码片段。它们可能很快就会过时。

## Testing Decisions

已做出的测试决策的列表。包括：

- 对什么是好测试的描述（只测试外部行为，而不是实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中类似的测试类型）

## Out of Scope

对此次重构范围之外事项的描述。

## Further Notes (optional)

关于此次重构的任何其他说明。

</refactor-plan-template>
