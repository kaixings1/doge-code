一个模糊的想法到来了——对单个 agent 会话来说太大了，而且笼罩在迷雾之中：从这里到**目的地**的路还不清晰。寻路（Wayfinding）是关于找到那条路，而不是猛冲向目的地。这个技能把这条路绘制成 repo 的 issue tracker 上的**共享地图**，然后逐个解决工单，直到路线清晰。

目的地因任务而异，而命名它是绘图的第一步——它决定了每一张工单。它可能是一份要交接并迭代打磨的 spec，一个要在规划开始前敲定的决策，或者一处就地完成的变更，比如数据结构迁移。这张地图是领域无关的——工程工作、课程内容，任何符合这个形态的东西都可以。

## 只规划，不执行

Wayfinder 默认是**规划**：每张工单解决一个决策，当地图完成时，意味着路已经清晰——在有人动手去实现之前，不再有需要决定的事。那种"干脆直接把活干了"的冲动，通常正是你已抵达地图边缘、该交接了的信号。任务可以在其 **Notes** 中覆盖这一点——把执行也纳入地图本身——但若无此约定，产出决策，而非交付物。

## 以名称指代

每张地图和每张工单都是一个 issue，因此都有一个**名称**——即其标题。在人类阅读的所有内容中——叙述、地图的 Decisions-so-far——都用名称指代，绝不用裸 id、编号或 slug。一堵写满 `#42, #43, #44` 的墙是读不懂的；名称一眼可读。id 和 URL 并不会消失——名称包裹着它的链接——但它们藏在名称*之内*，绝不取而代之。

## 地图

地图是本 repo issue tracker 上的单个 issue，标签为 `wayfinder:map`——它是权威产物。它的工单是地图的子 issue。

地图是一个**索引**，不是存储。它列出已做出的决策，并指向承载其细节的工单；一个决策只存在于一个地方——它的工单——所以地图绝不复述它，只摘出要点并附上链接。

**地图、其子工单、阻塞关系以及 frontier 查询在物理上存于何处，取决于具体的 tracker。** Issue tracker 应当已经提供给你——若未提供，运行 `/setup-matt-pocock-skills`。关于_本_ repo 如何表达这些操作，请查阅 tracker 文档的 "Wayfinding operations" 部分。若未提供任何 tracker，默认使用 local-markdown tracker。

### 地图正文

低分辨率的整张地图，每个会话加载一次。未关闭的工单**不**列在其中——它们是开放的子 issue，通过查询找到。

```markdown
## Destination

<走到这张地图尽头是什么样子——本任务正在寻找通往的那个 spec、决策或变更。一两行；每个会话在选择工单前都以此定位。>

## Notes

<领域；每个会话都应查阅的技能；本任务的既定偏好>

## Decisions so far

<!-- 索引——每个已关闭工单一行：足以判断相关性，再通过链接放大查看工单承载的细节 -->

- [<已关闭工单标题>](link) — <答案的一句话要点>

## Not yet specified

<!-- 见 "战争迷雾"：范围内、尚无法立为工单的迷雾；随着 frontier 推进而"毕业" -->

## Out of scope

<!-- 见 "Out of scope"：被判定超出目的地的工单；已关闭，永不"毕业" -->
```

### 工单

每张工单都是地图的一个**子 issue**；tracker 的 issue id 即其身份。其正文是那个问题，大小以一个 100K token 的 agent 会话为限：

```markdown
## Question

<本工单所要解决的决策或调查>
```

每张工单带有一个 `wayfinder:<type>` 标签——`research`、`prototype`、`grilling`、`task` 之一（见 [工单类型](#ticket-types)）。

一个会话通过把工单指派给驱动地图的开发者来**认领**它——必须在任何工作*之前*进行，这样并发的会话就会跳过它。这个指派人就是认领本身：一个开放且未指派的工单即未被认领。

阻塞关系使用 tracker 的**原生**依赖关系——这至关重要，因为它能在 tracker 自己的 UI 中把 frontier *可视化*呈现，人类无需打开地图就能看到哪些可领取。只有缺乏原生阻塞关系的 tracker 才退回使用正文约定。当阻塞某工单的所有工单都已关闭时，该工单即为**未被阻塞**；**frontier** 即开放、未被阻塞、未被认领的子工单——已知世界的边缘。

答案不属于正文——它在解决时记录（见 [逐张推进地图](#work-through-the-map)）。解决工单过程中产生的资产以链接方式挂到 issue 上，而不是粘贴进去。

## 工单类型

每张工单要么是 **HITL**——human in the loop，与一位亲自发言的人类协作推进——要么是 **AFK**，由 agent 独立驱动。HITL 工单只有通过那次实时交流才能解决；agent 绝不能代替人类那一方（一个自问自答的 grilling agent 已经破坏了这一点）。

- **Research**（AFK）：阅读文档、第三方 API 或本地资源如知识库。产出一份 markdown 摘要作为链接资产。当所需知识在当前工作目录之外时使用。
- **Prototype**（HITL）：通过制作一个廉价、粗糙、具体、可供反应的产物来提升讨论的保真度——一份提纲、一次粗略尝试、一个 stub，或通过 /prototype 技能产出的 UI/逻辑代码。将原型作为资产链接。当"它该长什么样"或"它该如何表现"是关键问题时使用。
- **Grilling**（HITL）：通过 /grilling 和 /domain-modeling 技能进行的对话，一次一个问题。这是默认情形。
- **Task**（HITL 或 AFK）：在*决策*得以做出之前必须完成的手工工作——没有要决定的、要原型化的或要调研的，但在它完成之前讨论被阻塞。比如注册某项服务以便评估其 API、开通访问权限、搬运数据以便看清其形态。这是唯一一个*去做*而非决定的类型——它之所以占有一席之地，是因为它为决策扫清了障碍，而不是因为它交付了目的地。agent 能独立完成的就独立驱动（AFK）；否则就交给人类一份精确的清单（HITL）。工作完成即解决；答案记录所做的工作以及任何后续工单将依赖的由此产生的事实（凭据位置、新的 URL、行数等）。

## 战争迷雾

地图是*有意*不完整的：不要绘制你还看不见的东西。在活跃工单之外，是**战争迷雾**——那些你明知将至却尚无法定型的决策与调查的模糊景象，因为它们悬而未决地依赖于仍开放的问题。解决一张工单，就拨开了它前方的迷雾，把现已可定型的内容"毕业"为新的工单——一次一张，直到通往目的地的路清晰、再无工单为止。

地图的 **Not yet specified** 部分就是写下这片模糊景象的地方：那个疑似的问题、那片日后要重访的区域。它是_朝向_目的地的未发现前沿——这里的一切都在范围内，只是还不够锐利、无法立为工单。写得粗略或详尽均可，视你的视野而定；它同时也可作为路标，让协作者了解这项任务的走向。

**迷雾还是工单？** 检验标准是你现在能否精确陈述那个问题——_而不是_你现在能否回答它。

- **立为工单，当**问题已经足够清晰——即使它被阻塞、你还无法对它采取行动。
- **放入 Not yet specified，当**你还无法如此清晰地表述它。不要预先把迷雾切成工单大小的碎片：它比一张工单更粗粒度，而且当 frontier 推进到那里时，一片迷雾可能毕业成好几张工单，也可能一张都不是。

**Not yet specified** 不包括已决定的（Decisions so far）、已经是活跃工单的，以及超出范围的（下一节）。

## Out of scope

迷雾只朝目的地一方聚集。目的地划定了范围，超出它的工单即 **out of scope**——它不是迷雾，也不属于 **Not yet specified**。它在地图上拥有自己的 **Out of scope** 部分：你有意识地排除在_本_任务之外的工单。让它落在这里的是范围，而非清晰度。

Out-of-scope 的工单永不毕业——frontier 止步于目的地——所以只有当目的地被重绘时它才会回归，而且那时也是作为一项全新任务，而不是旧任务的延续。

把某项工作判定为 out of scope 是一次范围界定行为，不是路线上的一个步骤。当一张已存在的工单被发现位于目的地之外——绘图时误划入范围，或被某次决策暴露——就**关闭它**（已关闭的工单明确不在 frontier 上），并在 **Out of scope** 部分留下一行：要点加上它为何超出范围，附上已关闭工单的链接。它不进入 **Decisions so far**——那里记录的是实际走过的路线，范围边界不是其上的一步。

## 调用

两种模式。无论哪种，**每个会话绝不多解决一张工单。**

### 绘制地图

用户带着一个模糊的想法来调用。

1. **命名目的地。** 运行一次 `/grilling` 和 `/domain-modeling` 会话，确定这张地图要寻找通往什么——那个 spec、决策或变更。目的地划定了范围，所以必须先行确定。
2. **绘制 frontier。** 再次 grilling，这次**广度优先**：在整个空间中铺开，而非在某个线程上深挖，浮现出尚未决定的决策以及现在就可以迈出的第一步。**如果这没有浮现出任何迷雾**——通往目的地的路已经清晰，整段旅程小到单次会话即可完成——那你就不需要地图。停下，询问用户希望如何继续。
3. **创建地图**（标签 `wayfinder:map`）：填入 Destination 和 Notes，Decisions-so-far 留空，把迷雾草拟进 **Not yet specified**。
4. **创建现在就能定型的工单**作为地图的子 issue——然后**第二轮**再接线阻塞边（issue 需要先有 id 才能互相引用）。接线将它们分入 frontier 和被阻塞两类；所有你还无法定型的留在迷雾中——即 **Not yet specified** 部分。
5. 停止——绘制地图是一个会话的全部工作；不要再解决工单。

### 逐张推进地图

用户带着一张地图（URL 或编号）来调用。工单是**可选的**——不给的话，由你选择下一个决策，而不是用户。

1. 加载**地图**——低分辨率视图，而非每张工单的正文。
2. 选择工单。若用户指定了一张，就用它。否则按顺序取第一张 frontier 工单。**认领它**：在任何工作之前先指派给自己。
3. 解决它——**按需放大**：按需获取任何相关或已关闭工单的完整正文；调用 `## Notes` 块中列名的技能。拿不准时，使用 `/grilling` 和 `/domain-modeling`。
4. 记录解决结果：把答案作为**解决评论（resolution comment）**发布，**关闭**该 issue，并在地图的 Decisions-so-far 中**追加一个上下文指针**。
5. 添加新浮现的工单（先创建后接线）；将答案使之可定型的迷雾毕业，把每一片毕业的迷雾从 **Not yet specified** 中清除，使其只以新工单的形式存在。如果答案揭示某张工单——这张或另一张——位于目的地之外，**将其判定为 out of scope**，而不是在路线上继续解决它。如果这个决策使地图的其他部分失效，更新或删除那些工单。

用户可能会并行运行未被阻塞的工单，所以要预期其他会话正在并发编辑 tracker。
