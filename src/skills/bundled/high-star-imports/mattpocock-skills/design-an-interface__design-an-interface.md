# 设计一个接口

基于《软件设计哲学》中的 "Design It Twice"（双重设计）理念：你的第一个想法不太可能是最好的。生成多个截然不同的设计，然后进行比较。

## 工作流程

### 1. 收集需求

在设计之前，先了解：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 有哪些关键操作？
- [ ] 有什么约束？（性能、兼容性、现有模式）
- [ ] 哪些应该隐藏在内部，哪些应该对外暴露？

询问："这个模块需要做什么？谁会使用它？"

### 2. 生成设计（并行子代理）

使用 Task 工具同时启动 3 个或更多子代理。每个子代理必须产出**截然不同**的方案。

```
每个子代理的提示词模板：

为以下内容设计一个接口：[模块描述]

需求：[收集到的需求]

本设计的约束：[给每个代理分配不同的约束]
- Agent 1："最小化方法数量——目标最多 1-3 个方法"
- Agent 2："最大化灵活性——支持多种用例"
- Agent 3："针对最常见的情况进行优化"
- Agent 4："从[特定范式/库]中汲取灵感"

输出格式：
1. 接口签名（类型/方法）
2. 使用示例（调用者如何使用它）
3. 该设计在内部隐藏了什么
4. 这种方法的权衡
```

### 3. 展示设计

展示每个设计时包括：

1. **接口签名** - 类型、方法、参数
2. **使用示例** - 调用者在实际中如何使用它
3. **它隐藏了什么** - 保留在内部的复杂性

依次展示各个设计，让用户在比较之前能够逐一消化每种方案。

### 4. 比较设计

展示完所有设计后，从以下方面进行比较：

- **接口简洁性**：方法更少、参数更简单
- **通用 vs 专用**：灵活性 vs 专注
- **实现效率**：接口形态是否允许高效的内部实现？
- **深度**：小接口隐藏大量复杂性（好） vs 大接口配以单薄的实现（坏）
- **正确使用的难易** vs **误用的难易**

用文字论述来讨论权衡，而不是用表格。突出各设计分歧最大的地方。

### 5. 综合

最佳设计往往融合了多个方案的洞见。询问：

- "哪个设计最符合你的主要用例？"
- "其他设计中有没有值得借鉴的元素？"

## 评估标准

来自《软件设计哲学》：

**接口简洁性**：方法更少、参数更简单 = 更容易学习并正确使用。

**通用性**：无需修改即可应对未来的用例。但要警惕过度泛化。

**实现效率**：接口形态是否允许高效的实现？还是会迫使内部实现变得别扭？

**深度**：小接口隐藏大量复杂性 = 深模块（好）。大接口配以单薄的实现 = 浅模块（避免）。

## 反模式

- 不要让子代理产出相似的设计——强制要求截然不同
- 不要跳过比较——价值就在于对比
- 不要进行实现——这里纯粹关乎接口形态
- 不要基于实现工作量来评估
