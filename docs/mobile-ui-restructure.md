# 手机客户端界面重构（单页 → 多页 + 底部导航）

> 日期：2026-10-07。起因：用户反馈「手机软件的功能太弱小，就基本上一个页显示
> 内容、一个连接页」。

## 问题诊断：不是功能少，是架构撑不住

用户反馈后先做清点，数据证实了这个判断：

| 指标 | 改造前 |
|---|---|
| Activity 数量 | **1 个**（`MainActivity.kt`） |
| `MainActivity.kt` | **1280 行、47 个方法** |
| 布局文件 | **2 个**（`activity_main.xml` 319 行 + `item_message.xml`） |
| 功能实现方式 | **9 个 AlertDialog 弹窗** |

**根本原因**：所有东西挤在一个类里，每个新功能只能退化成一个弹窗。
弹窗形式的功能有四个固有问题：

- 关掉就没了（无法停留、无法重复操作）
- 不能搜索、不能刷新
- 无法表达状态（如「当前连的是哪个会话」）
- 弹窗里的文字被压得很小，排障引导挤成一团

此前几轮我按「对标同类 APP 的功能清单」补能力 —— **那是功能点的罗列，
不是交互结构**。功能都在，但没有承载它们的界面结构。

## 改造方案：三页 + 底部导航

```
┌───────────────────────┐
│  ● 已连接             │  顶栏（三 tab 共享，全局看连接状态）
├───────────────────────┤
│                       │
│   Fragment 内容区      │  show/hide 切换，不重建
│                       │
├───────────────────────┤
│  [会话] [对话] [设置]  │  底部导航
└───────────────────────┘
```

| 页 | 内容 | 替代了什么 |
|---|---|---|
| **会话** | RecyclerView 列表 + 搜索 + 重新扫描 + 空态排障引导 | `SessionPickerDialog` |
| **对话** | 消息列表 + 活动区 + 输入栏（图片/语音/发送/中断）| 原 `activity_main.xml` 中段 |
| **设置** | 分组设置项 + 当前值显示 + 诊断入口 | 齿轮展开的连接面板 |

新增文件：`ChatFragment` / `SessionFragment` / `SettingsFragment` /
`SessionAdapter` + 4 个布局 + `SettingsActions` / `InputActions` /
`HostHistory` / `DraftStore`。

## 四个关键设计决策

1. **用 `show/hide` 而非 `replace`**。保活视图（对话页滚动位置不丢）。
   更重要的原因：`client` 的 `onEvent` 回调持有对话页控件引用，
   视图被销毁后会**空引用崩溃**。
2. **不用 `BottomNavigationView`**。需要引入 Material 库，而 3 个固定 tab
   用 `LinearLayout` + `TextView` 就够。按 YAGNI 阶梯：不引依赖。
3. **自动连接移出 Fragment 回调**。这是审查时发现的真实风险：连接成功会
   `append` 系统消息（依赖对话页 adapter 就绪），而两个 Fragment 的回调
   触发顺序由 `add` 顺序决定 —— 靠它保证前置条件太脆弱。改为所有视图
   就绪后由 `onCreate` 统一发起。
4. **拆类用宿主接口（`Host`）而非直接持有 Activity**。
   否则等于没拆，只是把耦合挪了个地方。

## 代码拆分：先拆边界最清晰的

`MainActivity` 按「是否依赖对话页控件」这条线拆：

| 抽出的类 | 行数 | 为什么先拆它 |
|---|---|---|
| `SettingsActions` | ~250 | **不碰对话页控件**，只用 Context + 少量状态 → 边界最清晰、风险最低 |
| `InputActions` | ~120 | 只依赖 `startActivityForResult` |
| `HostHistory` | ~50 | 纯字符串逻辑，零 Android 依赖 → **可单测** |
| `DraftStore` | ~40 | 同上，且边界有陷阱（空内容必须删键）|

**结果：`MainActivity` 1445 → 1231 行（-15%）**，职责变为「接线 + 对话协调」。

刻意**没有**一次性拆到「4 个协作类全拆完」——剩下的（`onEvent` /
`sendCurrent` / `append` / 权限弹窗）全部紧耦合对话页控件，
硬拆需要引入大量回调接口，收益不抵复杂度。**边界在哪拆到哪为止，
而不是凑数拆满。**

## 测试

| 文件 | 用例 | 覆盖 |
|---|---|---|
| `SessionFilterTest` | 10 | 会话搜索过滤（空查询返回全部、大小写不敏感、子串匹配）|
| `ConfigSnapshotTest` | 8 | 配置快照解析（**缺字段必须返回 null 而非编造默认值**）|
| `HostHistoryTest` | 10 | 地址历史（去重置顶、超限裁剪、序列化容错）|

Android 总计 **209 条 / 18 文件**全绿；TS **141 条 / 13 文件**全绿。
构建 + lint 通过。

变异验证（本轮 3 组，全部捕获）：

- 过滤逻辑「空查询返回全部」→ 返回空列表 → 1 条失败
- 配置解析「缺字段返回 null」→ 编造默认值 → 4 条失败
- （前轮）`merge` 去重、抑制判据、`requestId` 校验等

## 过程中的两次失误

1. **改 `activity_main.xml` 时直接 Write 覆盖**，丢了未提交的 8 个控件声明。
   好在 `MainActivity` 里的 `findViewById` 调用就是完整清单，据此重建了
   —— **代码即文档，控件引用不会丢**。
2. **设置页新增的 `onSettingsViewsReady` 与 `onChatViewsReady` 有顺序依赖**，
   自己审查时发现并改为在 `onCreate` 末尾统一发起（见设计决策 3）。

## 遗留

- `MainActivity` 仍有 1231 行，但剩余部分是「对话协调」这一件事，
  不再是「什么都往里塞」。继续拆的收益递减。
- 设置页的「当前值」依赖服务端 `session-info` 新增的 `config` 字段 ——
  老服务端不带该字段时显示「—」，这是刻意的（编造默认值比留空更误导）。
