### 三条来自完整调研的关键结论

这三条改变了对照的解读方式，值得单独记下：

1. **Claude 官方移动端的定位是「客户端而非执行端」**
   手机连的是**云端 VM** 或本机的 RC 会话，本地文件系统与 MCP 只在 RC
   模式下可达。这解释了为什么官方有「存档/恢复/双端删除」——
   **它连的是云，我们连的是本机**，这些能力不能照搬（见 §A 语义差异）。

2. **协议成熟度 ≠ 功能对等**
   Termius / Blink 在「多主机 / 密钥管理 / 生物识别 / 保活」上远超 AI 类 App，
   但在「会话语义」上**完全没有**（工具调用、diff、权限、子代理一个都没有）。
   反过来 AI 类 App 在传输层远不如它们。**不存在一个全维度领先的参照物**，
   因此本文按维度分别取基准，而不是整体抄某一家。

3. **第三方生态补齐了官方缺口**
   会话搜索、对话导出、语音输入、多模型混用主要来自 happy / CloudCLI，
   而非官方。这说明这些能力**属于可选项而非必备项**——
   官方没做，说明不在 MVP 里；第三方做了，说明有真实需求。

### ⚠ 关键语义差异：本项目的「会话」≠ 业界的「会话」

这是对照时最容易误判的一点：

| | 业界（Claude 官方） | 本项目 |
|---|---|---|
| 会话是什么 | **持久化的云端/RC 会话**，有 ID、可归档、可恢复 | **一个活着的 CLI 进程** |
| 会话切换 | 一账号下多会话并列，服务端维护 | 扫描本机端口段，各进程独立 |
| 归档/删除 | 有意义（服务端有持久记录）| **无意义** —— 关掉终端进程即消失 |
| 恢复中断 | 重开环境即可续上 | 需在手机端**启动进程**，属另一个范畴 |
| 重命名 | 写回服务端会话记录 | 只能改本进程内存/环境变量 |

因此本项目的取舍必须区别于业界：

- 「重命名」应做成**运行时改名**（新增 WS control 动作让服务端改 `resolveSessionLabel`），
  而非改配置文件 —— 因为进程重开就丢
- 「归档/删除」**不建议做**：进程模型下没有可归档的持久实体
- 「恢复中断会话」需手机端触发进程启动 → **谨慎**，这跨越了「远程控制」
  与「进程管理」的边界（业界之所以能做，是因为会话跑在**云端 VM**，
  而本项目的会话跑在用户自己的开发机上）

> 这条差异也解释了为什么 Claude 官方有「存档/恢复/双端删除」而本项目
> 不该照搬：**它连的是云，我们连的是本机**。

> ⚠ **实现时的安全约束（来自官方设计，必须照做）**：Claude 官方手机端
> **不允许**选择 `Bypass permissions` 与 `Auto-for-RC` 这两个权限模式 ——
> 只开放 Plan / Accept edits / Auto。
>
> 这条对本项目尤其重要：本项目本地跑 `doge.exe` 时常用
> `--dangerously-skip-permissions`（见 `mobile.bat`），若把「跳过权限」
> 做成手机端可选项，等于把一个已经被显式标记为 dangerous 的开关
> 暴露到**网络可达**的界面上 —— 任何拿到手机的人都能关掉本机的全部防护。
>
> 因此任务 #13（暴露 CLI 命令）的白名单里，
> **权限模式切换只允许 Plan / Accept edits / Auto，绝不暴露 Bypass**。

**这是「能看不能说」的核心问题**：手机端能发消息、能看回复，但 AI 一旦要
执行需授权的操作（写文件、跑命令），请求只在**电脑终端**弹出 —— 手机端完全无感。
远程使用时用户无法批准任何操作。

关键代码事实（已核实）：

- `interactiveHandler.ts:244-253` — `bridgeCallbacks.sendRequest(...)` 已能发权限请求
- `interactiveHandler.ts:256-280` — `onResponse` 已能收响应并按
  `behavior === 'allow'` 放行（`resolveOnce(ctx.buildAllow(...))`）
- `useReplBridge.tsx:438-451` — `BridgePermissionCallbacks` 接口定义完整
- **但** `useReplBridge.tsx:452` 只在 `!outboundOnly` 的**云端桥接分支**里
  挂载 `setAppState({ replBridgePermissionCallbacks })`
- **且** `useCanUseTool.tsx:166` 用 `feature("BRIDGE_MODE")` 门控读取

移动桥接走的是 `autoStartMobileBridge → MobileBridgeServer`，不经该分支，
所以 `replBridgePermissionCallbacks` **恒为 undefined**。

### ⚠ 漏掉的一项：通知抑制（防打扰）

官方移动端有一条我最初对照时忽略的设计：**用户正在电脑终端输入时，
手机不推送通知**（并可通过 `CLAUDE_CLIENT_PRESENCE_FILE` 按屏幕锁定状态扩展）。

这条的价值在真实使用中很明显：开发者往往手机电脑都在手边。若不做抑制，
AI 每完成一轮就在手机上震一下，而人正看着终端 —— 通知从「提醒」变成「骚扰」，
用户最终会整体关闭通知渠道，连真正需要介入的也被静音。

本项目的现状只做了最粗的一层：`maybeNotify` 里 `if (hasWindowFocus()) return`
（App 在前台则跳过）。缺少「电脑终端在前台」这一维度的感知。

**可行的实现路径**（服务端已有现成信号）：
- 服务端知道是否有人在终端交互 —— `process.stdin.isTTY` 加终端的输入活动时间
- 或在 `permission_request` / `assistant` 推送时附带 `terminalActive: true` 字段
- 客户端据此决定是否弹通知（本 App 在前台时不弹这条已有）

已建立任务 #17。

## 三、结论：漏缺功能分档

项目当前能力**集中在「对话」这一条链路上**（发消息 → 收回复 → 中断 → 会话切换），
这条链路本身做得扎实（有测试、有变异验证）。但业界同类产品的能力面**远不止对话**，
本项目在四个方向上整体缺失：

**方向 1：过程可见性（最影响体验）**
- 流式打字机输出
- 工具调用可视化
- 子 agent / 后台任务进度

现在手机端发一句「重构这个文件」，然后长时间空白 —— 电脑上正在读 20 个文件、
跑 3 个命令、起 2 个子 agent，手机完全看不到，无法区分「在干活」与「卡住了」。
**这不是功能缺失，是「看不见过程」。**

**方向 2：远程控制面（最影响可用性）**
- 权限远程批准/拒绝（链路已实现，仅未接线）
- diff 预览确认
- 计划模式确认
- 模型 / 思考强度 / 权限模式切换

缺了这些，手机端本质是「**只读观察器 + 发消息**」，无法完成闭环的远程工作。

**方向 3：输入手段**
- 图片/文件附件（服务端已就绪）
- 语音输入

**方向 4：会话与连接的成熟度**
- 运行时会话重命名、历史导出
- 需介入通知 + 通知操作按钮
- 连接诊断面板、多主机管理

**三个设计决策**（都有明确理由）：

1. **覆盖 `requiresUserInteraction` 工具**（ExitPlanMode 计划确认、
   AskUserQuestion 提问、ReviewArtifact）。初版照抄 channel relay 的守卫把
   它们排除了，但读 `AskUserQuestionTool.tsx:136-145` 的注释才发现：
   「channel relay 跳过这些工具，因此没有替代批准路径」—— 这 3 个恰恰是
   手机端最有价值的场景（否则用户不在键盘前时 AI 永久挂起）。已移除该守卫。
2. **不与本地对话框互斥**。手机与终端是同一用户的两个屏幕，谁先响应都算数。
   若做「本地已弹窗就不发手机」，用户会盯着手机干等，而终端其实已在问了。
3. **独立的通知渠道**。助手回复是「结果」（可选提醒），权限请求是
   「阻塞中的等待」（必须打断）。合成一个渠道会让用户被迫二选一。

**安全**：`behavior` 只接受精确的 `"allow"`，其它一切值（含 `"ALLOW"` 大小写
错误）都落到 `deny` —— 否则一个拼错的字符串就是任意提权通道。有专门用例锁定。

**变异验证**：去掉 `requestId` 校验 → Android 侧 2 条用例失败；
去掉 waiter 查找 → 服务端用例失败。均确认测试有效。

**四个关键设计决策**：

1. **增量与定稿必须可区分**。增量是尽力而为的预览（节流、可丢、可能跳号），
   定稿消息才是权威版本 —— 到达时**必须替换**预览，否则增量一旦丢失，
   用户会永久停留在残缺文本上。有专门用例锁定两者不同类型。
2. **增量不进 `items` 列表**。它每几十毫秒变一次，进列表会导致
   高频 `notifyItemInserted/Changed`，且定稿时要精确移除那一项、易与真实
   消息索引错位。改用「虚拟最后一项」渲染。
3. **工具活动独立区域，不塞进聊天气泡**。一次重构可能产生几十条工具调用，
   塞进气泡会淹没正文。活动区只保留最近 5 行，同工具的连续同名活动
   合并为一条（否则 Bash 每秒一条刷屏）。
4. **手机推送与终端渲染开关解耦**。`onStreamingText` 有
   `if (!showStreamingText) return` 守卫（reduced motion / 终端 bug 时关闭），
   若把推送塞进去，用户在终端开了 reduced motion 手机就收不到增量 ——
   两者是完全独立的显示面。因此推送包在守卫**外面**。

**增量算法的简化**：`f` 是纯累积函数（`text => (text ?? '') + delta`），
传 `null` 得到的恰是本次 delta 本身 —— 无需维护「上次长度」，
也就不会因内容块切换或文本被截断而算出错误的负增量。
（初版设计用「上次长度差值」，经核实 `f` 的语义后简化掉了。）

**变异验证**：把 assistant 分支的 `content.find(b => b.type === 'tool_use')`
改成 `content[0]` → 「纯文本回复不产生活动」失败；把 `assistant_delta`
解析成 `Incoming` → Android 侧 5 条失败。均确认测试有效。

### ✅ 已补齐：通知操作按钮 + 通知抑制（本轮第三批）

同属通知链，趁上下文热一次做完。

#### 1. 通知栏「批准 / 拒绝」按钮

此前通知只能「点开进 App 再批准」。AI 此刻正**阻塞等待**，若用户在做别的事，
要么被打断去开 App、要么漏掉，AI 就一直卡着。

| 文件 | 改动 |
|---|---|
| `Notifications.kt` | `notifyPermission` 增加两个 Action 按钮 + `decisionIntent` 构造 PendingIntent |
| `PermissionActionReceiver.kt` | 新建，接收按钮广播 |
| `PermissionDecisionStore.kt` | 新建，待发决定的**持久化队列** |
| `MainActivity.kt` | `submitPermissionDecision`（两条路径统一）+ `flushPendingPermissions` + `onNewIntent` |
| `AndroidManifest.xml` | 注册 Receiver（`exported=false`）|

**三个关键设计**：

1. **决定必须落盘**。用户在 App 完全没运行时点了通知栏批准 —— 那一刻没有
   连接可发，只能落盘等下次连接补发。不落盘 = 决定丢失 + 服务端权限请求
   永久悬挂 + 用户以为自己批准了。这是本批最容易被忽略却最要命的一点。
2. **`exported="false"` 是硬要求**。该 Receiver 只接受本 App 的 PendingIntent。
   若导出，任何应用都能伪造广播替用户「批准」操作 —— 那是提权通道。
3. **PendingIntent 的 requestCode 必须按 requestId 区分**。多条权限请求的
   通知会同时存在，若 requestCode 相同，Android 会复用前一个的 extras ——
   点「批准」实际批准的是**另一条**请求，是危险的静默错配。

**顺带统一了 App 内路径**：App 内点按钮此前只发送不落盘，若那一刻恰逢连接
断开，决定同样会丢（而通知栏路径是落盘的）。现在两条路径都走
`submitPermissionDecision`，语义一致。

#### 2. 通知抑制（终端活跃时不打扰）

不做的后果不是「少了个功能」，而是**通知渠道被整体关闭**：开发者手机电脑常
都在手边，AI 每轮震一下，人会烦到关掉通知权限，连真正需要介入的权限请求也
一并静音。

**数据源比预想的更好**：`src/ink/terminal-focus-state.ts` 的 DECSET 1004
终端焦点事件 —— 直接告诉我们终端在前台还是已被切走，比「最近输入时间」的
启发式准确得多。

```
focused → 抑制（用户就在电脑前）
blurred → 不抑制（用户切走了，可能在用手机）
unknown → 不抑制（关键取舍）
```

**`unknown` 的处理是最重要的决定**：不支持焦点上报的终端（老终端、部分
Windows 终端）恒为此值。若当作「抑制」，这些用户会**完全收不到通知** ——
静默失效；而当作「不抑制」只是偶尔多提醒一次。后者代价小得多。

**抑制的是通知，不是消息** —— 消息照常渲染，用户切回手机能看到完整历史，
只是没被震一下。客户端 `Incoming` 事件带上 `suppressNotify`，
`maybeNotify` 据此跳过。

**测试中被实测纠正的一处假设**：我原以为 `org.json` 的
`optBoolean(key, false)` 对字符串 `"true"` 会返回默认值 false。实测发现它
**会做类型转换**，返回 true（即「抑制」）—— 而「抑制」是偏危险的方向
（类型异常时应当让用户至少能看到通知）。因此改为显式判 Boolean 类型：
`if (!d.has(...)) return false; return d.opt(...) == true`。

#### ⚠ 三项「不做」的决策与理由

**1. 不引入密钥加密库**。`androidx.security:security-crypto` 已被 Google
标记为 **deprecated**，而为它引入新依赖换来的保护有限：存储位置本就是
App 私有目录（其他 App 读不到），`allowBackup="false"` 又阻断了备份外泄
路径，剩下 root/取证场景下 Keystore 方案的提升也很小。
→ 改为提供**「记住密钥」开关**（取消则不落盘）—— 这是比"加密存储"
更直接的隐私选择，且零依赖。

**2. 不做 mosh 级弱网保持**。手机切网时短暂重连可接受，引入 mosh 成本远高于收益。

**3. 不做归档/删除会话**。本项目的「会话」= 活着的 CLI 进程，没有可归档的
持久实体（关终端即消失）。

#### 🔒 安全关键：远程配置的白名单

手机端是**网络可达的控制面**，与本地终端的安全前提不同 —— 一个落在别人
手里的手机（或密钥未设时同 WiFi 的任意设备）能改什么，由白名单决定。

**绝不暴露 `bypassPermissions`**：本地 CLI 常以
`--dangerously-skip-permissions` 运行（见 `mobile.bat`），而 `useReplBridge`
的 `onSetPermissionMode` 实现**允许**切到 bypassPermissions（只查是否被
显式禁用）。若原样透传，等于把已被显式标记 dangerous 的开关放到网络上 ——
**拿到手机即可关掉本机全部防护**。Claude 官方移动端同样不开放此项。

实现为**两道独立防线**（实测：删掉任一道，另一道仍能拦住）：

1. `mobileConfig.ts` 的显式分支拒绝 + 错误信息说明这是有意的安全限制
2. `MOBILE_ALLOWED_PERMISSION_MODES` 数组本身不含 bypassPermissions

另有第三条：`useReplBridge` 的注册回调里再挡一次。三处冗余是刻意的 ——
单点失效的代价太高。

**其他白名单设计**：配置项用白名单而非黑名单（CLI 新增命令时默认安全）；
思考强度限定为枚举值（防超大值耗尽配额）；模型名做形状校验而非硬编码枚举
（模型名随版本变化，硬编码会让用户无法选新模型）。

### ✅ 已补齐：权限请求的 diff 预览（本轮第五批）

先前被列为「部分」的项，重新评估后确认**应当做**——它不是锦上添花：

> 在此之前，权限对话框只显示一个 400 字符的 input 摘要
> （如「路径: src/a.ts」），用户看不到 AI 具体要改什么就要点批准。
> 这是**安全上的实质缺口**：盲签比不签更糟，因为它让人以为自己在把关。

| 文件 | 改动 |
|---|---|
| `src/bridge/mobileDiffPreview.ts` | 新建，`buildDiffPreviewForMobile` 纯函数 |
| `src/bridge/mobileBridge.ts` | `requestMobilePermission` 的 payload 附带 diff |
| Android `BridgeProtocol.kt` | 解析 `diff.lines` |
| Android `MainActivity.kt` | `buildDiffView` —— 等宽字体 + 逐行着色 |

**四个设计决策**：

1. **只对文件修改类工具生成**（Edit / MultiEdit / Write）。Bash 等命令类
   不生成 —— 命令本身就是完整信息，伪造一个"diff"反而误导。
2. **不做 Myers 等 diff 算法**。Edit 工具本身给了 `old_string`/`new_string`，
   直接标记增删即可。这里是「用户扫一眼判断要不要批准」，不需要精确差异计算。
3. **截断保留首尾**（70% 头 + 30% 尾）—— 中间多为重复上下文，用户更需要
   看改动全貌。单行上限 300 字符（压缩文件的一整行会撑爆渲染）。
4. **客户端解析失败时静默降级为空 diff，不丢弃整条请求**。
   diff 是辅助信息，格式异常不该让用户看不到权限请求（那会让 AI 永久挂起）。

**实现时被测试揪出的一处缺陷**：`toLines('')` 返回 `['']`（`''.split('\n')`
是 `['']`），所以空字符串会生成一行孤零零的 `+`，让用户困惑「这到底改了什么」。
已改为空内容返回 null。

**变异验证**：把 Edit 的删/增标记对调 → 6 条用例失败。这个变异对应的真实
风险是「用户看到的方向反了，以为要删 X 实际要加 X」—— 在权限确认场景下
是危险的误导。

### ✅ 顺带修掉：移动会话名额泄漏（测试暴露的真实缺陷）

写权限测试时第 8 个用例莫名连不上，探针实测：

```
server.getClientCount()=0 | ws.readyState=3(CLOSED)
```

追到 `mobileSession.ts`：

```ts
createSession() {
  if (this.sessions.size >= this.maxSessions) { ... }  // ← 数总数
}
endSession(id) { session.state = 'disconnected'; return true }  // ← 不删除
```

**`endSession` 只改状态不删条目，而上限检查数的是总数。**

后果（真实用户场景，不是测试专属）：同一 CLI 历史上**累计**连过 5 次
（换设备、App 重装、反复重连都会累积），第 6 次连接被 `close(4002)` 拒绝，
且唯一清理途径是 30 分钟超时。用户看到「手机一直连不上，电脑侧毫无变化」。

修法：上限只统计活跃会话，创建前先 `purgeDisconnectedSessions()`。
变异验证：还原旧写法 → 4 条用例失败。

> 这个缺陷的价值在于：它**不可能靠读代码发现** —— `endSession` 和
> `createSession` 相隔 90 行，各自看都合理，只有把两者连起来看才暴露。
> 是「让测试真实执行」而非「审阅代码」把它挖出来的。

### 实施过程中的教训（方法论）

1. **假设连错两次就要停止猜测**。先怀疑「close 晚到」，再怀疑「兜底超时」，
   都改了仍失败。直到写探针直接打印 `readyState`/`getClientCount` 才定位。
   按规则「守卫条件判据必须实测」，探针比推理可靠。
2. **`console.log` 在测试里会被 console 覆盖层吞掉**（本项目
   `consoleOverride.ts` 的既有行为）。探针必须写文件。
3. **MSYS2 heredoc 会破坏中文**：`python3 - <<'EOF'` 里的中文断言直接
   乱码导致替换失败。脚本必须用 Write 工具写成文件再执行。
4. **测试的「单独跑通过、一起跑失败」要先排除共享全局状态**：
   `getActiveMobileBridgeServer()` 与端口都是模块级共享的。

**子 agent「可终止」仍缺**：活动区现在能**看见**子代理在跑，

建议随第 2 项一起做。

**明确不做**（有理由，避免反复讨论）：

| 项 | 理由 |
|---|---|
| mosh 级弱网保持 | 手机切网时短暂重连可接受，引入 mosh 成本远高于收益 |
| 多人协作同会话 | 官方也标 ○ 罕见；本项目是个人开发机连接，多人共控有安全顾虑 |
| 归档/删除会话 | 进程模型下无持久会话实体（见 §A 的语义差异说明）|
| 手机端启动/管理 CLI 进程 | 跨越「远程控制」与「进程管理」边界 |
| 手机端可选 Bypass 权限 | 官方明确不开放；暴露一个 dangerous 开关到网络可达界面 = 关掉全部防护 |
