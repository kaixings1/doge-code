# A. 开发与实现 (Development)

## /tdd — 测试驱动开发

**用途**: 按红-绿-重构循环逐步构建功能，确保代码通过测试驱动开发。

**使用前提**: 无

**触发场景**:
- 用户要求编写新功能并希望先写测试
- 用户提到 "TDD"、"测试先行"、"红绿重构"
- 修复 bug 时希望添加回归测试

**输入参数**: 无

**完整命令**:
```
> /tdd
```

**执行流程**:
1. **规划阶段**: 确认需要什么接口变更，测试哪些行为，获得用户批准
2. **示踪弹**: 写一个测试(RED) → 写最少代码使其通过(GREEN)
3. **增量循环**: 逐个添加行为，每次一个测试 → 最少实现
4. **重构**: 所有测试通过后，提取重复代码，应用 SOLID 原则

**输出结果**:
```
✅ RED: 测试失败（未实现功能）
✅ GREEN: 代码编译通过，测试通过
✅ 重构完成，5 个测试全部通过
```

**最佳实践**:
- 测试描述行为，而非实现细节
- 只为当前测试编写足够的代码
- 不要预测未来的测试

## /implement — 根据 PRD 实现代码

**用途**: 根据 PRD 或 Issues 实现代码，使用 TDD 确保质量。

**使用前提**: 项目根目录下有 PRD.md 或 Issues 列表

**触发场景**:
- 用户说 "实现这个功能"、"开始编码"
- PRD 或 Issue 描述清晰且可执行

**输入参数**: PRD 引用或 Issue 编号

**完整命令**:
```
> /implement PRD.md
> /implement #123 #124 #125
```

**执行流程**:
1. 阅读 PRD/Issue 了解需求
2. 使用 TDD 逐步实现每个功能点
3. 运行类型检查和测试套件
4. 使用 /review 进行审查
5. 提交到当前分支

**输出结果**:
```
✅ 已实现功能: 用户认证模块
✅ 运行 12 个测试，用时 3.2s
✅ 类型检查通过
✅ 提交了 3 个 commits 到 feature/auth 分支
PR: https://github.com/org/repo/pull/456
```

## /batch — 并行编排大型更改

**用途**: 研究并规划大规模更改，然后在 5-30 个隔离的工作树代理中并行执行，每个代理都会打开一个 PR。

**使用前提**: 必须在 git 仓库中

**触发场景**:
- 用户希望跨多个文件进行机械性的批量更改（如迁移、重构、批量重命名）
- 更改可以分解为独立的并行单元

**输入参数**: 描述要进行的更改指令

**完整命令**:
```
> /batch 把所有 lodash 的使用替换为原生等效
> /batch 从 react 迁移到 vue
> /batch 为所有无类型函数参数添加类型注释
```

**执行流程**:
1. **计划模式**: 研究代码库，找出所有需要更改的文件
2. **分解单元**: 将工作分解为 5-30 个自包含单元
3. **确定 e2e 测试方案**: 找出如何验证更改
4. **编写计划**: 保存到计划文件
5. **启动工人**: 使用隔离的 git worktree 并行执行
6. **跟踪进度**: 实时更新状态表

**输出结果**:
```
| # | 单元 | 状态 | PR |
|---|------|--------|----|
| 1 | 添加类型到 auth/ | done | PR: https://... |
| 2 | 添加类型到 utils/ | done | PR: https://... |
| 3 | 添加类型到 api/  | running | — |

24 个单元中有 22 个作为 PR 落地
```

## /simplify — 代码审查与清理

**用途**: 审查更改后的代码以提高复用性、质量和效率，然后修复发现的任何问题。

**触发场景**:
- 用户说 "审查"、"清理"或"简化"
- 代码更改完成后需要优化

**输入参数**: (可选) 额外关注领域，如 `/simplify 检查性能`

**完整命令**:
```
> /simplify
> /simplify 检查安全性
```

**执行流程**:
1. 运行 `git diff` 查看更改
2. 启动三个平行审查 Agent：
   - 代码复用审查 (寻找可替换的现有工具)
   - 代码质量审查 (检测 hacky 模式、冗余状态等)
   - 效率审查 (检测 N+1、重复计算等)
3. 聚合发现并直接修复

**输出结果**:
```
✅ 代码审查完成
- 修复: 使用现有 utils/path 而非手写路径处理
- 修复: 删除重复的状态变量，改用派生值
- 修复: 并行化两个独立的 API 调用
```

# B. 调试与诊断 (Debugging)

## /diagnosing-bugs — 系统化 Bug 诊断

**用途**: 硬 Bug 的系统化诊断循环，包含构建反馈回路、重现最小化、假设检验、修复和回归测试。

**触发场景**:
- 用户说 "diagnose" / "debug this"
- 遇到崩溃、异常、失败、性能下降

**输入参数**: 问题描述或错误信息

**完整命令**:
```
> /diagnosing-bugs 我的应用在处理大文件时崩溃
> /diagnosing-bugs TypeError: Cannot read property 'x' of undefined at src/handler.ts:42
```

**执行流程** (6 个阶段):

### 第 1 阶段: 构建反馈循环
创建在 bug 出现时为 red 的测试/脚本。尝试顺序：
1. **Failing test** at whatever seam reaches the bug
2. **Curl / HTTP script** against a running dev server
3. **CLI invocation** with a fixture input
4. **Headless browser script** (Playwright / Puppeteer)
5. **Replay a captured trace**
6. **Throwaway harness** (minimal subset)
7. **Property / fuzz loop** (1000 random inputs)
8. **Bisection harness** (git bisect run)
9. **Differential loop** (old vs new version)
10. **HITL bash script** (drive human with a script)

**完成标准**: Red-capable, Deterministic, Fast (seconds), Agent-runnable

### 第 2 阶段: 重现 + 最小化
运行循环，观看它 go red。然后 shrink the repro to the smallest scenario.

### 第 3 阶段: 假设检验
Generate 3-5 ranked, falsifiable hypotheses. Each hypothesis must state its prediction.

### 第 4 阶段: Instrumentation
Each probe must map to a specific prediction from Phase 3. Change one variable at a time.

### 第 5 阶段: Fix + 回归测试
1. Turn the minimised repro into a failing test
2. Watch it fail
3. Apply the fix
4. Watch it pass
5. Re-run against the original scenario

### 第 6 阶段: 清理 + 事后
- Original repro no longer reproduces
- Regression test passes
- All debug instrumentation removed
- Throwaway prototypes deleted
- State the correct hypothesis in commit/PR

**输出结果**:
```
## Bug 诊断完成

### 根因
`parseInput()` 在第 42 行没有处理 `null` 输入，导致 TypeError。

### 修复
添加 null 检查 guard 在函数入口。

### 回归测试
✅ 新增测试: should handle null input gracefully
✅ 原始场景不再复现
✅ 所有 15 个 tests 通过
```

# C. 设计与架构 (Design)

## /grilling — 深入设计审查

**用途**: relentless 追问用户关于计划或设计的每一个细节，直到双方达成共识。

**触发场景**:
- 用户希望在构建前验证计划的可行性
- 使用任何 grill 触发词（"确定吗"、"再想想"、"检查一下"）

**完整命令**:
```
> /grilling
```

**执行流程**:
- 沿着设计树的每个分支逐个解决决策之间的依赖关系
- 对每个问题提供你的推荐答案
- 一次问一个问题，在继续之前等待反馈
- 如果问题可以通过探索代码库回答，则改为探索

**输出结果**: 逐轮对话，最终达成共识的设计方案。

---

## /grill-with-docs — 追问 + ADR + 术语表

**用途**: 与 /grilling 相同，但同时创建 ADRs 和术语表到 CONTEXT.md。

**触发场景**:
- 有代码库需要记录决策时
- 设计讨论后需要固化架构决策

**完整命令**:
```
> /grill-with-docs
```

**执行流程**:
1. 运行 /grilling 采访用户
2. 运行 /domain-modeling 捕获已解决术语
3. 为难以逆转的决策创建 ADRs
4. 更新 CONTEXT.md

**触发场景**:
- 不需要代码库或持久化时

```

```

## /codebase-design — 深度模块设计

**用途**: 深度模块设计词汇表 — 设计小接口、深实现的模块。

**触发场景**:
- 设计或改进模块接口
- 决定接缝位置
- 使代码更可测试

**完整命令**:
```
> /codebase-design
```

**关键术语**:
- **模块**: 拥有接口和实现的任何东西
- **接口**: 调用者必须知道的一切
- **深度**: 单位接口的行为量 (目标: 小接口 + 大实现)
- **接缝**: 可以改变行为而不编辑那里的地方
- **杠杆率**: 调用者每学习一个接口获得的能力

## /obsidian-vault — Obsidian 笔记管理

**用途**: 在 Obsidian 知识库中搜索、创建和管理笔记。

**触发场景**:
- 在 Obsidian 中查找、创建或组织笔记

**完整命令**:
```
> /obsidian-vault
```

**约定**:
- 所有笔记使用标题大小写
- 不使用文件夹，使用 wikilinks 和索引笔记
- 使用 `[[wikilinks]]` 链接到相关笔记

---

## /memory-manage — 持久化记忆管理

**用途**: 管理持久化记忆（MEMORY.md 用于项目知识，USER.md 用于用户偏好）。

**触发场景**:
- 保存项目知识或用户偏好
- 在会话之间共享信息

**输入参数**: add/replace/remove + store(agent/user) + 内容

**完整命令**:
```
> /memory-manage add agent "本项目使用 bun 而非 npm"
> /memory-manage add user "我偏好简洁的回复，不带结尾总结"
> /memory-manage list
> /memory-manage replace agent "旧知识" "新知识"
> /memory-manage remove agent "过时的信息"
```

**记忆类型**:
- `agent` (MEMORY.md) — 项目环境事实、约定、工具特性
- `user` (USER.md) — 用户角色、偏好、沟通风格

## /remember — 记忆审查

> **仅限 ANT 用户**: `/remember` 技能仅在 USER_TYPE=ant 时可用。

**用途**: 审查自动记忆条目，提议将其提升到 CLAUDE.md、CLAUDE.local.md 或共享记忆。

**触发场景**:
- 清理 CLAUDE.md、CLAUDE.local.md 和自动记忆中的过期或冲突条目
- 审查、整理或提升自动记忆条目

**完整命令**:
```
> /remember
```

**输出**: 按行动类型分组的结构化报告:
1. **提升** — 移动条目到 CLAUDE.md/local.md
2. **清理** — 重复项、过时条目、冲突
3. **模糊** — 需要用户确认目的地
4. **无需操作** — 应保留不动

# F. 系统 & 配置 (System & Config)

## /update-config — 配置 Claude Code

**用途**: 通过 settings.json 配置 Claude Code harness — 权限、环境变量、hooks。

**触发场景**:
- "允许 npm 命令"
- "添加权限"
- "设置 DEBUG=true"
- "当 Claude 停止时显示消息"

**完整命令**:
```
> /update-config 允许 npm 命令
> /update-config 设置 DEBUG=true
> /update-config 我希望在写入文件后运行 prettier
```

**工作流程**:
1. 明确意图 (模棱两可时使用 AskUserQuestion)
2. 读取现有 settings.json (从不替换)
3. 合并新设置 (特别注意数组合并)
4. 编辑文件
5. 确认更改

**钩子事件**:
| 事件 | Purpose |
|------|---------|
| PermissionRequest | 运行在权限提示之前 |
| PreToolUse | 运行在工具执行之前 |
| PostToolUse | 运行在工具执行之后 |
| PostToolUseFailure | 运行在工具失败后 |
| Stop | Claude 停止时运行 |
| PreCompact | 压缩前 |
| UserPromptSubmit | 用户提交提示时 |
| SessionStart | 会话开始时 |

## /schedule — 定时远程代理 (Scheduled Agents)

**用途**: 创建、更新、列出或运行按 cron 调度执行的远程代理。

**触发场景**:
- 安排定期运行的远程代理
- 设置自动化任务
- 管理定时触发器

**完整命令**:
```
> /schedule 每天检查仓库并在 main 分支部署
> /schedule list
> /schedule run <trigger-id>
```

**Cron 表达式示例**:
| 表达式 | 含义 |
|--------|------|
| `0 9 * * 1-5` | 每个工作日 UTC 上午 9 点 |
| `0 */2 * * *` | 每 2 小时 |
| `0 0 * * *` | 每天 UTC 时间午夜 |
| `30 14 * * 1` | 每周一 UTC 下午 2:30 |

## /resolving-merge-conflicts — 解决 Git 冲突

**用途**: 解决正在进行的 git merge/rebase 冲突。

**触发场景**:
- git merge/rebase 过程中出现冲突

**完整命令**:
```
> /resolving-merge-conflicts
```

**执行流程**:
1. 查看当前状态 (git 历史和冲突文件)
2. 找到原始来源 (理解每个变更的原因)
3. 解决每个冲突块
4. 运行自动化检查 (类型检查、测试、格式化)
5. 完成 merge/rebase

**用途**: 设置 PreToolUse hook 阻止危险 git 命令。

- 防止破坏性 git 操作
- 添加 git 安全钩子

```
> /git-guardrails
```

- `git checkout .` / `git restore .`

## 技能激活规则

### 用户激活 (User Invocable)
用户可以直接输入 `/<skill-name>` 来调用这些技能。

### 模型激活 (Model Invocation)
某些技能会在模型检测到特定模式时自动激活。例如：
- `/claude-api`: 当代码中导入 `anthropic` 时自动激活
- `/tdd`: 当用户提到 "TDD" 或 "测试先行" 时激活
- `/debug`: 当用户报告 "卡住" 或 "报错" 时激活

### ANT 专属
以下技能仅在 `USER_TYPE=ant` 时可用:
- `/verify`
- `/remember`
- `/lorem-ipsum`

---

> **注意**: 技能数量可能会随版本更新而变化。使用 `/ask-matt` 可以获取当前最新的技能推荐。
