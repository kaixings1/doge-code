### 实施中修正的两处评估判断

**1. D4「服务端需接线」的判断被推翻，但方向相反**
评估说「需新增服务端能力」，实施时确认：**服务端完全不需要改动**。
理由：文本附件的本质是「把文件内容变成 prompt 的一部分」，
拼进 message 后走既有 `enqueue` 路径即可。这比评估预期更简单。

**2. D3 的 sessionId 陷阱（评估未发现）**
评估只说「显示恢复命令」，实施时发现：移动桥接的 `sessionId` 是
自造的 `mobile-<时间戳>`，**与 `--resume` 需要的 doge 会话 ID 完全不同**。
若直接显示「`doge.exe --resume mobile-1234567`」，用户敲了必然失败 ——
比不显示更糟。故新增了 `resumeSessionId` 字段回传真实 ID，
并写了专门的测试锁定「两者必须不同」。

### 实施中修出的一个真实缺陷

`withEditIfLast` 初版只过滤 `DELETE`，导致**不幂等** ——
连续调用两次会累积出两个「编辑并重发」菜单项。
被单测「幂等：连续调用两次不出现两个编辑项」抓出，已修。

## D4 非图片附件 —— 已按路径 B 实施

### ⚠️ 一处被推翻的假设（记录过程，避免重复踩坑）

**初判**：服务端 `resolveAndPrepend` 已就绪，移动端只需接线，约 10 行。

**实测后推翻**。勘察 `inboundAttachments.ts` 的实际实现：

```ts
// 1. 提取 —— 只接受 uuid 与文件名，没有内容
const attachmentSchema = z.object({
  file_uuid: z.string(),
  file_name: z.string(),
})

// 2. 解析 —— 靠 uuid 去**远端下载**，不是从消息里读内容
async function resolveOne(att) {
  const response = ...
  data = Buffer.from(response.data)     // ← 从远端 API 取
  await writeFile(outPath, data)
}
```

即这套附件机制的设计前提是：**文件先被上传到某个远端服务，消息里只带
`file_uuid`，服务端再按 uuid 下载回来**（注释提到「web 创作器」）。

**移动端没有这个 uuid 体系** —— 手机选的文件在手机上，没有先上传到
那个远端服务。所以「接上 `resolveAndPrepend` 就能用」是不成立的。

### 实际采用的路径（路径 B）

**只支持文本类附件，内容直接拼进 prompt，零落盘**：

```
手机选文件（SAF，无需存储权限）
→ 扩展名白名单校验（TextAttachment.isSupported）
→ 体积校验（上限 200K 字符）
→ 拼进 message（带 --- 文件名 --- 分隔标记）
→ 走既有 sendMessage → enqueue 路径
```

**服务端零改动**。这是与评估预期的最大出入 ——
评估说「需新增服务端能力」，实施后确认不需要。

**为什么用白名单而非黑名单**：黑名单永远会漏（新二进制格式层出不穷），
白名单在遇到未知格式时默认拒绝 —— 安全方向正确。
且有专门测试覆盖「伪装的 `.txt.exe` 按最后一段判断」。

**为什么不做路径 A（上传二进制 + 服务端落盘）**：
会引入整类安全问题（写入路径、体积炸弹、符号链接攻击），
而手机端发附件的真实场景（贴日志、贴配置、贴代码片段）恰好都是文本。

## D3 会话恢复 —— 已按「轻量版」实施

> **实施结果**：会话详情页新增「恢复此会话」区，显示
> `doge.exe --resume <真实会话ID>` 并支持复制。
>
> **实施中发现的关键陷阱（评估未预见）**：移动桥接的 `sessionId` 是
> 自造的 `mobile-<时间戳>`，与 `--resume` 需要的 doge 会话 ID **完全不同**。
> 若直接显示前者，用户敲了必然失败 —— 比不显示更糟。
>
> 修法：`session-info` 新增 `resumeSessionId` 字段，用
> `getSessionId()` 取真实 ID；取不到时为 `null`，客户端据此**不显示**
> 恢复命令。有专门测试锁定「两者必须不同」。
>
> 未采用「手机端触发恢复进程」：跨越「远程控制」→「进程管理」边界，
> 风险高（一个 bug 就能在用户机器上反复拉起进程）。评估已否决。

### 现状

CLI 侧有 `--resume` / `-r` 参数（会话恢复能力存在），
但**没有任何「启动一个新 CLI 进程」的接口** —— 桥接是**被动**的：
它只监听已存在的 CLI 进程。

### 核心矛盾

「在手机上恢复会话」意味着：手机发指令 → 服务端**启动新进程** → 新进程的桥接
监听某端口 → 手机连上它。

这需要服务端能做进程管理。而当前架构下：

1. 桥接随 CLI 进程存活，CLI 退出桥接就消失（`mobileBridge.ts` 的 `stop()`）
2. 没有任何模块负责「按需拉起 doge.exe」
3. 手机端已经能扫描端口段（`SessionScanner`），但扫的是**已存在的**进程

### 可行路径

**路径 A（推荐）**：不做「手机启动进程」，改做「**列出可恢复的历史会话**」
· 服务端扫描会话文件（`~/.claude/projects/*/`），返回可恢复的会话列表
· 用户在手机上选一个 → 服务端**在现有进程内**切换会话？

**但**：`/resume` 是 `local-jsx` 命令（需 Ink UI），手机端无法触发 ——
与之前 `/model` 的约束相同。而换会话实质是换整个对话上下文，
比换模型的影响面大得多。

**路径 B**：外部启动器
· 用户自己写好 `restore.bat`（`doge.exe --resume <id>`），手机端**只是显示**
  这个命令让用户复制到电脑执行
· 零风险、零改动，但体验没提升 —— 用户还是要回电脑

**路径 C（不建议）**：服务端 fork 进程
· 需要：进程管理、端口分配、崩溃清理、孤儿进程回收
· 这跨越了「远程控制」与「进程管理」的边界
· 风险：一个 bug 就能在用户机器上反复拉起进程

### 建议

**先做路径 B 的轻量版**：在会话详情页加「恢复此会话的命令」——
显示 `doge.exe --resume <sessionId>` 并支持复制。
零风险，且把「怎么做」这个信息给了用户（当前他连这个都不知道）。

路径 A 需要先回答「换会话是否要清空当前上下文」这个产品问题 ——
若答案是「要」，那它等同于「关闭当前对话重开」，用户体验上并不比
「另开一个终端」好。**建议暂缓，等有明确需求再评估。**

## D2 消息编辑重发 —— 已实施（收窄为「编辑最后一条用户消息」）

> **实施结果**：长按最后一条用户消息 → 「编辑并重发」→ 编辑框 → 提交。
> 服务端新增 `editMessage` control 动作 + `setMobileEditHandlers` 注册机制
>（与权限审批同一模式：REPL 挂载时注入，因为它才拿得到消息 uuid）。
>
> **实施前的关键验证**：评估里标记「`removeTranscriptMessage` 可能从未被
> 真正跑过」—— 实施前先读了实现，确认它是**通用**的
>（按 UUID 从会话文件移除，只读尾部 + 位置写入 + 截断），
> 且注释明确说「目标几乎总是最近追加的条目」—— 正好匹配本场景，疑虑解除。
>
> **实施中修出的缺陷**：`withEditIfLast` 初版只过滤 `DELETE`，导致
> 不幂等 —— 连续调用会累积出两个「编辑并重发」项。被单测抓出并修复。

### 关键发现：撤回机制**接收端已就绪，发送端缺失**

勘察证据：

| 组件 | 状态 |
|---|---|
| `TombstoneMessage` 类型定义 | ✅ `src/types/message.ts:198` |
| `removeTranscriptMessage(uuid)` 实现 | ✅ `src/utils/sessionStorage.ts:1511` |
| **它的唯一调用点** | ✅ `REPL.tsx:2577`（处理收到的 tombstone）|
| **tombstone 的产生点** | ❌ **不存在** |

即：这套机制是「**消费端完整、生产端从未实现**」。Grep 全库
`'tombstone'` 字面量在 `.tsx` 下零匹配。

### 为什么这对 D2 是好消息

「编辑重发」的语义 = 撤回旧消息 + 用新内容重发。前半段（撤回）的
**基础设施已经有了**（`removeTranscriptMessage`），只是没有入口。

需要新增：
1. 服务端：一个 control 动作 `editMessage(uuid, newText)`
   → 调 `removeTranscriptMessage(uuid)` + `enqueue(newText)`
2. 客户端：长按菜单加「编辑重发」（仅对**最后一轮回合之后**的消息可用）

### 风险与边界

**必须限制可编辑范围**。理由：改历史中间的消息会让后续所有消息的上下文
失效（AI 是基于包含旧内容的上下文生成的回复）。

· 只允许编辑**最后一条 user 消息** —— 此时它之后只有 AI 的回复，
  撤回它等同于「重新提问」，语义清晰
· 编辑更早的消息 = 需要把后续全部撤回，用户预期不明确 → **不做**

另一个边界：**AI 已经开始处理那条消息时不能编辑**（会与正在进行的
回合冲突）。需要判断回合状态。

### 建议

**可以做，但范围收窄为「编辑最后一条用户消息」**。
约服务端 30 行 + 客户端 60 行。价值：用户打错字不必重新打一遍，
且比「删除本地 + 重发」更符合直觉（后者会在对话里留两条）。

## D1 多会话同屏 —— 不建议做

### 架构约束（量化证据）

| 指标 | 值 |
|---|---|
| 依赖 `messageQueueManager` 的文件 | **33 个** |
| 其中的模块级单例状态 | **3 处**（`commandQueue` / `snapshot` / `queueChanged`）|
| 队列消费方 `useQueueProcessor` 的订阅方式 | `useSyncExternalStore`（**单队列，无会话概念**）|

`useQueueProcessor.ts` 的结构：
```ts
const queueSnapshot = useSyncExternalStore(subscribeToCommandQueue, getCommandQueueSnapshot)
// 无 sessionId 参数 —— 整个进程只有一个队列
```

### 要改成多会话，必须动的地方

1. `messageQueueManager` 的队列**按 sessionId 分桶**，`enqueue()` 加目标参数
   → 触及全部 33 个调用方
2. `useQueueProcessor` 按当前激活 sessionId 消费
3. `useReplBridge` 的推送 effect 按 sessionId 过滤（否则 A 会话的回复
   会推给正在看 B 的手机）
4. REPL 需要一个「当前激活会话」的概念 + 切换 UI

### 回归风险

`messageQueueManager` 被这些路径共用：**任务通知、subagent、斜杠命令、
权限请求、proactive tick、bash 命令**。任一处的行为变化都会波及所有交互。

而 `useQueueProcessor` 的运行环境是 React + Ink，**无法单元测试** ——
改造后主要靠真机验证，回归成本极高。

### 更根本的质疑：这个功能真的需要吗

「多会话同屏」的收益是**省一个终端窗口**。而代价是：

· 改造所有交互共用的队列基础设施
· 失去进程级隔离（现在每个会话独立进程，一个崩不影响另一个）
· 上下文串味风险（A 会话的消息进入 B 的上下文）

反观现状（多进程 + 手机端切换）：
· 已有会话列表、按主机分组、标记「当前」
· 切换成本 = 一次点击（已优化过）
· 进程隔离天然保证不串味

**建议不做。** 若将来确实需要，先做用户调研：多会话的实际使用频率有多高？
若只是「偶尔切一下」，当前方案已经够用。

## 建议的实施顺序

若决定推进，按此顺序（风险从低到高）：

| 序 | 项 | 理由 |
|---|---|---|
| 1 | **D3 轻量版**（显示恢复命令）| 零风险，且解决了「用户不知道该怎么做」这个实际问题 |
| 2 | **D4 路径 B**（仅文本类附件）| 零落盘、零安全风险、实现量最小；覆盖手机端的主流需求 |
| 3 | **D2 编辑最后一条** | 撤回基础设施已就绪，但需处理回合状态判断 |
| ❌ | D1 多会话同屏 | 33 文件改动 + 无法单测 + 收益存疑 |

## 未验证的前提（实施前必须实测）

1. **`removeTranscriptMessage` 在常规路径下的效果** ——
   代码注释提到「orphaned message」（孤立消息）场景，
   需确认对**已正常写入 transcript** 的消息是否同样有效。
   因为它目前只有一个调用点（处理收到的 tombstone），而
   tombstone 的产生端从未实现 → **这条路径可能从未被真正跑过**。
2. **WS 帧大小上限** —— 附件体积受此约束。当前无显式限制，
   需实测大文件行为（尤其通过 `adb reverse` 的 USB 通道）。
3. **`prependPathRefs` 的产物格式** —— 它拼出的 `@路径` 引用
   在 AI 侧如何被消费（是否会被自动读取为文件内容）。
   若不成立，附件的实际价值会大打折扣。

## 评估结论

**线 D 四项没有一项是「接线即用」的** —— 这与线 A/B/C 的性质不同：

| 线 | 性质 | 原因 |
|---|---|---|
| A/B/C | 客户端为主，服务端已就绪或无需服务端 | 手机端缺的是界面与组织，功能本体在 |
| D | 服务端架构层面缺失 | 四项都需要新增服务端能力，而非接线 |

这也是把 D 单独作为一条线、且在 A/B/C 之后才评估的原因 ——
它的成本量级不同。**建议：先做 D3 轻量版（零风险），
D4 路径 B 次之，D2 再次，D1 不做。**
