# 隧道模式下的多会话切换 — 方案评估（待决策）

> 状态：**调研完成，待用户决策**。本文只做方案梳理与权衡，不含实现。
>
> 相关文档：
> - `android/MULTI-SESSION-PLAN.md` — 方案 A（每会话一进程一端口 + 端口段扫描），已实现
> - `docs/mobile-multi-session-plan-b-assessment.md` — 方案 B（单进程多对话），**不建议实施**

---

## 1. 问题定义

现有「多会话切换」（方案 A）依赖**在局域网内扫端口段**发现多个会话：

```
SessionScanner.scan(host, 5680..5689)
   → 对 host 的每个端口 GET /mobile/session-info
   → 收齐「活着的」会话，列给用户切换
```

这在 **LAN / USB** 下成立，因为每会话 = 一个独立 CLI 进程 = 一个独立**本地端口**。

**隧道（TUNNEL）下这条路走不通**，原因是根本性的：

| 事实 | 后果 |
|---|---|
| cloudflared **快隧道**是「一个公网子域 ↔ 一个本地端口」的**一对一**映射 | 一条隧道只暴露**一个**会话 |
| 公网侧**只开 443**（HTTPS/WSS），不开放 5680-5689 等本地端口 | 扫 `域名:5680..5689` 全部超时 |
| 快隧道的子域**每次启动随机**（`xxx.trycloudflare.com`） | 地址不稳定，用户每次要重填（本文第 4 节单独讨论） |

**结论**：要让隧道模式支持「一个 App 切换多个本机会话」，必须**改变会话如何暴露到公网**。下面是所有可行路径。

---

## 2. 可行方案（按改动量从大到小）

### 方案 T1：多隧道 —— 每会话一条隧道

**做法**：桌面端启动脚本在检测到多个会话（多个端口在监听）时，**为每个会话各起一条 cloudflared 隧道**；把 `{label, cwd, port, wssUrl}` 列表写到本地文件或一个查询端点；App 在隧道模式下**拉这个列表**替代端口扫描。

**数据流**：

```
桌面 (start-mobile-bridge.mjs --tunnel)
  ├─ 发现会话 in 6000..6009（各 GET /mobile/session-info）
  ├─ 对每个活会话: cloudflared tunnel --url http://127.0.0.1:<port>
  └─ 汇总 → 写 .doge/tunnels.json:
         [{ "label":"修CI", "cwd":"D:\\proj", "port":6000,
            "wss":"wss://abc.trycloudflare.com/mobile/ws" }, ...]

App (TUNNEL 模式)
  └─ 拉列表（从哪拿？见下）→ 显示会话列表 → 点选 → 连该 wss
```

**关键难点**：App 怎么拿到那个列表？
- **T1a**：列表也用一条隧道暴露（一个"索引隧道"指向 `tunnels.json` 的服务端点）。→ App 需先知道**索引隧道**地址（仍要填一次，但只有一个且可固定）。
- **T1b**：桌面端把列表写进**第一个会话的响应**（复用 `/mobile/session-info`，加一个 `siblings[]` 字段列出全部会话的 wss）。→ App 连上任一隧道即可拿到全表。
- **T1c**：App 手动填一条隧道地址，服务端在 `session-info` 里回传 `siblings[]`（同 T1b，但强调"从任一入口都能发现全部"）。

**成本**：
- 桌面脚本：起 N 条隧道（N = 会话数）+ 轮询端口段 + 汇总写文件/改 session-info。中等。
- 服务端：`/mobile/session-info` 增加 `siblings[]`（需知道兄弟会话说起哪几个端口 + 各自的公网 wss —— 公网 wss 是**每条隧道各自的随机子域**，服务端得从桌面脚本注入的配置里读）。中等。
- App：TUNNEL 下把"扫端口"换成"拉 siblings 列表"。小。

**优点**：真·多会话，与 LAN 体验对齐。
**缺点**：
- **每会话一条隧道 = 每会话一个随机子域** → N 个地址要管理，且都会变（见第 4 节）。
- cloudflared 免费快隧道**并发多条**是否有速率/数量限制，需实测。
- 复杂：桌面脚本要管 N 个 cloudflared 子进程的生命周期。

---

### 方案 T2：聚合端点 —— 一个端口列出所有会话

**做法**：**不动隧道数量**（仍一条隧道↔一个会话），但让**这一个会话的服务端**能回传"本机所有会话"的信息。App 连上隧道后，调 `/mobile/sessions`（新端点）拿到全表，再逐个切换。

**但关键矛盾**：App 要**连到另一个会话的 WSS**，而那个会话的 WSS 地址**只有它自己的隧道才有**。所以 T2 **必须配合 T1**——聚合端点只能给出"有哪些会话 + 它们的本地端口/标签"，**给不出可公网访问的 wss**（除非 T1 也为它们开了隧道）。

**除非**：所有会话共用**同一条隧道**（见 T3）。

**成本**：服务端加一个 `/mobile/sessions` 端点（列出本机端口段探测到的所有会话）。小。
**优点**：简单。
**缺点**：**单独不够**——列出来的会话没有公网入口，切过去连不上。**必须与 T1 或 T3 组合**。

---

### 方案 T3：单隧道 + 路径路由（反代到一个"总服务"）

**做法**：**只起一条隧道**，指向一个**新增的聚合服务**；该服务按**路径或子域名**把请求转发到不同会话。

两种子形态：
- **T3a 路径路由**：`wss://域名/s/6000/mobile/ws`、`wss://域名/s/6001/mobile/ws` —— 聚合服务按 `/s/<port>/` 前缀转发到 `127.0.0.1:<port>`。
  - 问题：现有 `mobileBridge.ts` 的 WS 路径固定是 `/mobile/ws`，且各会话是**独立进程**、各自监听端口。需要**前面加一个反代层**（新进程）做路径→端口映射。
- **T3b 子域路由**：cloudflared **命名隧道**支持配置多个 hostname → 不同本地端口（`a.example.com → 6000`，`b.example.com → 6001`）。**需要自有域名 + Cloudflare 账号**（见第 4 节）。

**成本**：
- T3a：**要写一个反代进程**（Node http-proxy，WS 升级要透传），并改造启动脚本。较大；且要处理"聚合服务自己也是单点"。
- T3b：**配置为主**（cloudflared config.yml 里配 ingress 规则），**无需写反代**。但需要域名 + 账号。

**优点**：
- **T3b 是最优雅的**：一条命名隧道、多个固定 hostname、每个指向一个会话端口；地址**永久固定**（同时解决第 4 节）。App 只需把 `base domain` 记一次，`/sessions` 列表里的 hostname 直接可用。
- T3a 无需域名，但也有固定地址（前提是快隧道能不随机——见第 4 节，快隧道做不到）。

**缺点**：
- T3b 依赖用户有域名 + Cloudflare 账号（门槛）。
- T3a 要写并维护一个反代进程。

---

### 方案 T4：不做多会话，隧道只连"当前一个"

**做法**：隧道模式**只支持单会话**（现状）。要多会话就**用 LAN/USB**，或**开多条隧道手动切**（每条隧道一个地址，App 地址栏填不同地址）。

**成本**：**零**（现状即此）。
**优点**：不增加复杂度。
**缺点**：隧道下无法像 LAN 那样一键切会话。

---

## 3. 方案对比表

| 方案 | 多会话 | 需要域名/账号 | 需要写反代 | 地址是否固定 | 改动量 | 备注 |
|---|---|---|---|---|---|---|
| T1 多隧道 | ✅ | 否 | 否 | ❌（快隧道随机） | 中 | N 个随机地址，难管理 |
| T1b+T2 | ✅ | 否 | 否 | ❌ | 中 | 从任一入口发现全部 |
| T3a 路径路由 | ✅ | 否 | **是** | ⚠（快隧道仍随机） | **大** | 要维护反代进程 |
| **T3b 命名隧道多 hostname** | ✅ | **是** | 否 | **✅ 固定** | 中（配置为主） | 最优，但有门槛 |
| T4 单会话 | ❌ | 否 | 否 | — | 零 | 现状 |

**初步倾向**（待你定）：
- **有域名/账号** → **T3b**：一次配置，多会话 + 地址永久固定，都解决。
- **无域名** → **T1b + T2**：桌面起多隧道，用 `siblings[]` 让任一入口都能列出全部；地址仍随机（配合第 4 节的"自动下发"缓解）。

## 4. 隧道地址固定（独立于多会话，但强相关）

cloudflared 快隧道（`--url`，无需账号）的子域**每次随机**。要固定地址有三条路：

### 4.1 命名隧道（固定，需账号）
- 需 **Cloudflare 账号 + 自有域名**（域名托管在 Cloudflare）。
- 一次配置：
  ```yaml
  # ~/.cloudflared/config.yml
  tunnel: <tunnel-id>
  credentials-file: <uuid>.json
  ingress:
    - hostname: doge.example.com
      service: http://127.0.0.1:6000
    - service: http_status:404
  ```
  ```cmd
  cloudflared tunnel create doge
  cloudflared tunnel route dns doge doge.example.com
  cloudflared tunnel run doge
  ```
- **地址永久固定** `wss://doge.example.com/mobile/ws`。**同时天然支持多会话**（多 hostname 各指一个端口 → 即 T3b）。
- **门槛**：要有域名；域名要迁到 Cloudflare 托管；首次要 `cloudflared tunnel login`（浏览器授权）。

### 4.2 自动下发新地址（无需账号，缓解随机）
- 保留快隧道（随机子域），但**桌面端把当前隧道地址写到"App 能拿到的地方"**，App 自动获取，不用手输。
- **难点**：App 要拿到地址，得先能连上某个东西 —— 鸡生蛋问题。可行办法：
  - **4.2a 写入同一局域网**（**推荐，无需账号**）：复用**已有的 UDP 广播**机制。
    - 现状：`src/bridge/mobileBeaconSender.ts` 已在广播 `{sessionId, port, cwd, label, interactive, clients}`（局域网被动发现）。
    - 改动：给广播 payload **加一个 `tunnelUrl` 字段**（当前快隧道的 `wss://…/mobile/ws`）；桌面端一旦建立隧道就把它塞进去，每次广播动态取（同现有做法，端口/标签都是动态取）。
    - App 侧：`BeaconProtocol`/`BeaconListener`（android）解析该字段；收到后**自动写入 TUNNEL 模式的地址存储**（`last_url_TUNNEL`）。
    - 用户体验：**在家/公司（同一 WiFi）开一次 App → 自动获得最新隧道地址** → 出门（切 4G/5G）直接用，不必手输。
    - 边界：广播是 UDP 多播，**只在同一局域网有效**（出门后收不到新广播，但**已存下的地址仍可用**，直到电脑端重启换子域）。
    - 成本：**小**（服务端加字段 + App 加解析/落盘）。**这是无账号条件下最优的缓解**。
  - **4.2b 固定一个"跳板"**：用户自备一个**永远在线的地址**（如那个命名隧道，或某个 VPS），App 从跳板拉当前快隧道地址。→ **又需要固定地址**（回到 4.1）。
  - **4.2c 剪贴板/二维码**：桌面端打印二维码/写入剪贴板，用户扫/粘一次。→ 半自动。

### 4.3 结论
- **真正"固定"只有 4.1（命名隧道）**，代价是域名 + 账号。
- 4.2 只能"自动获取新地址"，且大多**需要先同 WiFi 或已有固定跳板**，无法纯无账号地做到"永远固定"。

---

## 5. 建议的决策路径

```
用户有域名/Cloudflare 账号？
 ├─ 是 → T3b 命名隧道（一条隧道多 hostname）
 │         └─ 同时解决：多会话（各 hostname 一个会话）
 │                      地址固定（域名永久）
 │         └─ 改动：桌面启动脚本支持 --named-tunnel <域名>；App 支持从 /sessions 拿列表
 │
 └─ 否 → T1b + T2（快隧道多开 + siblings 列表）
           ├─ 桌面：为每个会话起一条快隧道，把 siblings[] 注入 session-info
           ├─ App：TUNNEL 下拉 siblings 列表代替端口扫描
           └─ 地址仍随机 → 加 4.2a（同 WiFi 时自动更新地址）缓解
```

## 6. 待确认的问题（决策前需要你回答）

1. **你有 Cloudflare 账号 + 自有域名吗？**（决定走 T3b 还是 T1b+T2）
2. **隧道下你实际需要几个会话并发？**（2-3 个 vs 很多，影响是否值得多隧道）
3. **能接受"首次在同一 WiFi 下自动同步地址，之后出门用"吗？**（4.2a 的前提）
4. **多会话切换的入口**：放在现有「会话」页（扫描列表）还是隧道专属的列表？
