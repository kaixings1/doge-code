# 手机端功能扩展规划（v2）

> 日期：2026-10-07。起因：用户反馈「功能、设置都太单一、简单，还可以进一步细化、丰富」，
> 并要求「任务比较多，需要加的功能也是，有必要计划、实施」。
>
> 本文是**规划**，不是实施记录。实施进度看末尾的对照表。

## 一、先诊断：为什么会「单一」

改造前的清点（见 `mobile-ui-restructure.md`）：

| 指标 | 值 |
|---|---|
| Activity | 1 个 |
| 布局 | 2 个 |
| `MainActivity.kt` | 1280 行 / 47 个方法 |
| 功能实现方式 | 9 个 AlertDialog |

**「单一」不是功能数量问题，是三个结构性缺失：**

1. **没有信息层级** —— 所有东西都在一个平面。会话只是一个列表项，
   配置只是一个选项列表，没有「概览 → 详情 → 操作」的分层。
2. **没有设置体系** —— 设置页只有 4 组 13 个控件，且都是「要么服务端配置、
   要么什么都没有」。缺少**纯本地偏好**这一类（外观、消息、通知、安全），
   而这类恰恰是用户感知最强的部分。
3. **功能只到「能用」** —— 每项只做最小闭环：能连、能发、能看。
   没有面向实际使用的深化（搜索、快捷输入、批量操作、状态回显）。

## 二、扩展的四条线

按「用户能感知的程度」排序，不按实现难度。

### 线 A：设置体系（纯本地偏好，不依赖服务端）

这是**投入产出比最高**的一条 —— 全部是客户端本地状态，不需要服务端配合，
且用户立刻能感知。

| 组 | 项 | 类型 | 说明 |
|---|---|---|---|
| **外观** | 主题 | 三选一 | 深色 / 跟随系统 / 浅色 |
| | 字号 | 三选一 | 小 / 中 / 大（影响消息与界面） |
| | 消息密度 | 二选一 | 紧凑 / 舒适（气泡间距） |
| | 时间显示 | 二选一 | 绝对（14:30）/ 相对（3 分钟前） |
| **消息** | 流式显示 | 开关 | 关闭则等定稿再显示（省电/省流量） |
| | 自动滚动 | 开关 | 新消息到达是否自动滚到底 |
| | Markdown 渲染 | 开关 | 关闭则显示纯文本（排障用） |
| | 代码块高亮 | 开关 | 当前是轻量着色，可关 |
| **通知** | 回复通知 | 开关 | 对应 `doge_reply` 渠道 |
| | 需介入通知 | 开关 | 对应 `doge_action` 渠道 |
| | 终端活跃时抑制 | 开关 | 已有服务端标志，此处可关掉 |
| | 通知声音/震动 | 开关 | 细粒度控制 |
| **安全** | 记住密钥 | 开关 | 已有 |
| | 危险操作二次确认 | 开关 | 切 Bypass、清空记录等 |
| | 待发权限决定 | 入口 | 查看/清空队列（已实现 queue，缺 UI） |

### 线 B：信息层级（会话与对话的深化）

| 位置 | 现状 | 扩展 |
|---|---|---|
| 会话 | 一行摘要 | **分组**（按主机分节）+ **排序**（端口/标签/活跃）+ 详情页 |
| 对话 | 气泡 + 输入框 | **搜索**（高亮跳转）+ **快捷指令面板** + 滚动到底按钮 |
| 消息 | 长按复制 | 长按弹菜单：复制全文 / 复制代码块 / 引用 / 删除本地 |
| 活动区 | 只读 | 按工具类型分组 + 可折叠 + 耗时显示 |

### 线 C：功能深化（每项从「能用」到「好用」）

| 功能 | 现状 | 深化 |
|---|---|---|
| 历史 | 单调 500 条 | 按日期分组、支持删除单条/某天、导出格式可选（MD/纯文本/JSON） |
| 诊断 | 静态文本 | 记录失败历史（最近 N 次）、可清日志、显示网络类型 |
| 远程配置 | 只能选 | 显示当前值来源（环境变量/配置/默认）、改动历史 |
| 扫描 | 手动点 | 记住上次会话、自动重扫间隔、局域网网段可配 |

### 线 D：待评估（需服务端配合，成本高）

这些不在本轮做，但记录以便将来决策：

| 项 | 为什么暂缓 |
|---|---|
| 多会话同屏监控 | 需要服务端支持多路推送 + 客户端多连接并存，架构改动大 |
| 消息编辑重发 | 需要服务端支持「撤回并重发」语义，当前协议无此概念 |
| 会话恢复（--resume） | 需手机端触发进程启动，跨越「远程控制」边界 |
| 附件（非图片） | 服务端 `resolveAndPrepend` 支持，但手机端文件选择 UI 复杂 |

## 三、实施顺序与理由

按「独立性 + 用户感知」排，不做并行（避免同时改多个页面导致回归难定位）。

| 序 | 批次 | 内容 | 为什么这个顺序 |
|---|---|---|---|
| 1 | **#28 设置体系** | 线 A 全部（14 项 + 分组） | 纯本地、零依赖、立刻可见；且它是后续功能（如「消息密度」影响对话页）的**配置基础** |
| 2 | **#29a 对话页** | 搜索、快捷面板、长按菜单、滚动按钮 | 对话页是使用频率最高的页面 |
| 3 | **#29b 会话页** | 分组、排序、详情页增强 | 依赖 #27 已建的详情页 |
| 4 | 线 C 深化 | 历史管理、诊断历史、配置来源 | 建立在前三批之上 |
| 5 | 线 D | 需服务端配合，单独评估 | — |

## 四、约束（必须遵守）

1. **每批完成后真机验证**。这次教训：编译 + 220 条单测 + lint 全过，
   装上后启动即崩。真机运行不可替代。
2. **本地偏好必须有默认值且默认值 = 当前行为**。否则升级后用户会看到
   界面突变，而他没有改过任何设置。
3. **优先扩展现有页面，不新建页面**。页面数量已够（3 主 + 4 二级），
   再加会稀释导航效率。
4. **新增设置项要有说明文字**。参照 `ConfigFragment` 的做法 ——
   用户看到「消息密度：紧凑」时不知它影响什么。
5. **可测试的逻辑抽成纯函数**。设置项的「取值合法性」与「默认值回落」
   最容易被写错（且错了是静默的），必须可单测。

### 线 C 的三项改动（2026-10-07）

**C1 历史管理**（`HistoryStore` + `HistoryFragment`）
· 此前只能「整体清空」——用户不知道存了多少、占多大、哪个最占地方
· 现在：列出所有会话历史（条数/大小/相对时间）、单个删除、全部清空（二次确认）
· **安全关键**：`delete` 的入参来自列表项，故加了文件名白名单守卫
  （前缀后缀匹配 + 只允许 `_.-` + 拒绝 `..`）。有 8 条守卫测试，
  含一条「`keyFor` 的产物必须被 `isSafeName` 接受」的双向契约测试 ——
  否则会出现「自己生成的历史自己删不掉」

**C2 诊断历史**（`DiagnosisLog` + 诊断页新增分区）
· 此前只保留**最近一次**失败，且成功连接后被清空。用户遇到间歇性断连时
  回到 App 看到的永远是「暂无失败记录」——而那正是最需要信息的时候
· 现在：保留最近 20 条（时间/原因/HTTP码/当时地址），诊断页展示最近 5 条
· 只记失败不记成功：成功次数对排障无价值，只记失败更聚焦

**C3 配置来源显示**（服务端 `currentMobileConfig` + 客户端 `ConfigSourceLabels`）
· 此前只显示当前值，用户「改不成」时完全无法解释原因
· 现在每项标注来源：手机设置 / 环境变量 / 配置文件 / 默认
· 最需要这个的场景：用户设了 `CLAUDE_CODE_EFFORT_LEVEL` 之类的环境变量，
  改手机端设置不会生效 —— 界面现在会显示「（环境变量）」

### 一处测试方法论的自我纠正

写 C2 测试时我先写了两条**复刻型测试**（在测试里重新实现一遍顺序与裁剪
逻辑，而不是调用生产代码），并在注释里辩解说"这是验证语义契约"。
想清楚后发现那就是复刻 —— 生产代码改动时它不会失败。

改法：把 `append` 里的「插入 + 裁剪」抽成纯函数 `prepend(existing, record, max)`，
测试直接调用它。这样才有约束力（变异测试确认：把裁剪方向从「丢最旧」
改成「丢最新」，对应用例失败）。

### 本轮的两次设计发现

1. **同名函数的语义可以相反**：`ChatSearch.findMatches` 空查询返回**空**，
   而 `SessionFragment.filterSessions` 空查询返回**全部**。理由是用户意图不同
   （还没开始搜 vs 想看列表）。已在代码注释写明，避免将来被"顺手合并"。

2. **动态菜单项优于固定菜单**：长按菜单按消息内容决定是否显示
   「复制代码块」——不含代码块的消息不显示，避免出现点了没反应的项。
   这类判定被抽成 `MessageActions.availableActions` 以便单测。
