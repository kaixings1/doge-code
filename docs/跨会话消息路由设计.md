## 方案

### 1. 会话发现（解析层）
- 输入框 `@session-name` → 在本地已知会话注册表查 `sessionId`。
- 注册表数据源：本地桥 `localBridge` 已维护 `sessions_updated` 广播（mobileBridge:1411），复用其会话清单。
- 解析落在 `processUserInput` 现有 mention 处理旁（line 591 附近），把 `@名` 转成 `agent_mention` attachment 携带 `targetSessionId`。

### 2. 路由投递（通道层）
- 目标 session 在同一进程 → 直接 `context.enqueue`/注入消息（同进程 REPL 总线）。
- 目标 session 在另一进程 → 走本地桥 5678（`localBridge.ts` 的 `broadcast`）。
- **双保险防回灌**（遵守 .dogerules 广播回灌环路守则）：
  - 服务器端：`broadcast(sessionId, msg, excludeWs=senderWs)`（localBridge 注释已记录旧版未排除发送者的坑）
  - 客户端：消息按 `direction: 'outbound'` / `source` 标记过滤自己发出的回声

### 3. 权限上浮
- 跨进程投递需目标 session 的权限上下文批准（参照本地桥既有 `bridgePermissionCallbacks.ts`）。
- 跨会话消息默认走 `ask` 或静默失败（不自动执行危险工具）。

## 风险

- 会话注册表跨进程一致性：依赖本地桥会话清单的准确性，休眠/分离场景可能陈旧 → 解析失败时降级为普通文本（不阻断主流程）。
- 回灌环路：必须双保险，单端修复会复发（前车之鉴见 .dogerules）。
- 权限：跨会话消息不应绕过目标 session 的工具审批。

## 验证

- 变异测试：删 `excludeWs` 或客户端 `direction` 过滤 → 端到端脚本复现「A 收到自己回声」失败。
- 手动：两终端各开一个 doge-code 会话，A 输入 `@B 你好`，B 收到、A 不自回声。
